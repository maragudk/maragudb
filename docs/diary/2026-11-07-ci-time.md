# Diary: Cut the test time of the slowest packages

CI gives each package 600 s. On run 42355346670, for commit 020e781, `internal/sim` took 412 s, `internal/sqllogictest` 289 s, and the root package 147 s. Each feature adds simulator configurations, and run-to-run differences on the CI runner are large: the same `internal/sim` code took between 234 s and 412 s. If a package goes over the limit, CI fails for a reason that has nothing to do with correctness. This task cuts the time and keeps detection the same.

## Step 1: Set the requirement and the verification

**Author:** main

### Prompt Context

**Verbatim prompt:** Build independently, this is an experiment
**Interpretation:** CI is green, but `internal/sim` used 69% of its limit. The margin must come back before the next feature adds more.
**Inferred intent:** Keep CI as a gate that can be trusted. It must not fail at random, and it must not lose coverage to stay fast.

### What I did
I wrote the requirement and gave it to the builder `ci-time`.
- **Target.** With `GOMAXPROCS=4 go test -race -count 1`, each of `internal/sim`, `internal/sqllogictest`, and the root package takes at most about 60% of its current local time. That is the time that `go test` reports, before and after. The CI runner was up to about 4.7 times slower than a local run, so this gives back the margin.
- **Find where the time goes first.** The builder measures before it cuts. Possible causes are serial tests that could run in parallel, configurations that duplicate each other, setup repeated per test, or work that belongs in the soak.
- **No loss of detection.**
  - The kill matrix keeps every verdict, detected or not, cell by cell. The seed that detects a mutant may change, and every reason for an undetectable cell stays valid.
  - Every STATE is still reached in `make test`.
  - Every requirement ID keeps its coverage.
- **Moved, not deleted.** Work that leaves `make test` goes into `make soak`. Nothing is removed.
- **Changes to CI itself.** The shared workflow takes no timeout input, so changes to it are out of scope. Splitting a package or adding sharding inside this repo is allowed if it keeps one `go test ./...`.

### Why
A gate that fails at random gets ignored, and a gate that stays fast by testing less gives a false signal. This experiment depends on the tests alone, so both kinds of failure matter.

### What worked
Nothing to report yet.

### What didn't work
Nothing failed in this step.

### What I learned
On run 42355346670 every package was slower than on the run before it: sqllogictest went from 178 s to 289 s and the root package from 87 s to 147 s. The runner itself varies a lot, not only the simulator.

### What was tricky
Nothing yet. To keep the kill matrix exact while the corpus changes, some seeds may need to be chosen again.

### What warrants review
The kill matrix diff and the list of what moved to `make soak`.

### Future work

## Step 2: Profile the four slowest packages and cut their time

**Author:** ci-time

### Prompt Context

**Verbatim prompt:** You are the builder `ci-time` for maragudb (/Users/maragubot/Developer/maragudb; work on main in that checkout; commit to main, do NOT push — the lead pushes). [...] Goal: Each of internal/sim, internal/sqllogictest, and the root package takes at most ~60% of its current local time (`GOMAXPROCS=4 go test -race -count 1 -shuffle on`, the time `go test` reports; measure before and after, a few runs each). internal/engine too if cheap. [...] Constraints: no loss of detection [...] Work removed from `make test` goes into `make soak`, not deleted. List what moved in the diary.
**Interpretation:** Find where the time goes in `internal/sim`, `internal/sqllogictest`, the root package, and `internal/engine`, and cut each to about 60% without changing a kill matrix verdict, an unreached STATE, or a requirement's coverage.
**Inferred intent:** Give CI back its margin under the 600 s limit per package without making the gate weaker.

### What I did
I measured first, with `go test -json` for the time of every test, `-cpuprofile`, and `/usr/bin/time` for CPU against wall time.

- **Profile.** The four packages took 85.7, 49.7, 41.0, and 33.8 s (mean of three runs). `internal/sim` used 3.8 of 4 CPUs, so only less work helps. `TestMutants` was 238 of 321 CPU seconds. Its 79 cells with a "cannot" reason ran all 20 seeds every time: 1,580 of 1,987 mutant runs, only to confirm the reason. `internal/sqllogictest` used 1.2 CPUs: it waited for Postgres. One file, `random/select/slt_good_0.test`, spent 22 s in Postgres alone, on 5-way cross joins with `DISTINCT` (about 2 ms each, because Postgres sizes a hash table from estimates of tables that were never analyzed), and it ran last. The root package and `internal/engine` had no `t.Parallel` at all, and their tests share nothing.
- **Root and engine** (`/maragudb_test.go`, `/store_test.go`, `/store_internal_test.go`, `/maragudb_internal_test.go`, `/internal/engine/*_test.go`): every top-level test calls `t.Parallel()`. Subtests stay serial, because helpers such as `loadedWorlds` are not safe for concurrent subtests. `TestDiskCacheHelperProcess` stays serial; it only runs as a helper.
- **sqllogictest** (`/internal/sqllogictest/run.go`, `/internal/sqllogictest/corpus.go`): `shardStarts` splits the read-only queries at the end of a file (a `query` whose SQL is a SELECT without INTO) into shards of at most `shardQueries` (3,000 in `TestCorpus`). Every shard after the first runs on a fresh maragudb and a fresh Postgres schema that first run the records before the queries again, uncounted. A file with a transaction statement runs in one sequence. The report adds the shards up to the first with a difference, so it counts what a run in one sequence counts. A `slots` channel bounds the shards that run at the same time to the workers, which are now three per CPU. `largestFirst` starts the largest files first. `postgres` now takes a schema name.
- **Kill matrix** (`/internal/sim/sim_test.go`, `/internal/verify/catalog.go`, `/internal/verify/doc.go`): in `make test` a cell with a "cannot" reason tries seeds 1 to 5 (`cannotSeeds`). With `-update` (`make verification`) or `MARAGUDB_SOAK` set, it tries all 20 (`allSeeds`). The kill matrix records the new field `cannotSeeds`, and /docs/verification.md says which target tries how many seeds.
- **Moved to `make soak`:** seeds 6 to 20 of the 79 cells that cannot detect their mutant. `make soak` now starts with `MARAGUDB_SOAK=1 go test ./internal/sim -run TestMutants`, which runs the whole kill matrix with every seed and compares it with the golden file. `make verification` still runs all of it too. Nothing else moved.
- **Self-review** with the code-review skill at medium found eight points. I fixed four: shards had no bound on Postgres connections (now `slots`), a file's counts after a mismatch included later shards (now the merge stops at the first shard with a difference), general sharding replayed every write of files such as `index/delete` (now only the read-only end is split, which needs only the setup again and also cut CPU from 78 s to 66 s), and every shard lexed the records before it again (now `setup` is computed once). I answered `readOnly` and `nextval` with a comment: maragudb rejects state-changing functions, so Postgres never runs them. I kept three as they are: fewer seeds in `make test` for cells that cannot detect (the brief allows the move to `make soak`), `TestDB_Tigris` in parallel (see below), and sharding inside a file instead of shards as jobs of the worker pool (the slots give the same bound).
- A writer sub-agent drafted the README sentences and the two decisions in /docs/decisions.md; I corrected them after the review changed the sharding.

Timings, `GOMAXPROCS=4 go test -race -count 1 -shuffle on`, three interleaved runs before and after (`git stash` of the change between runs):

| Package | Before | After | After / before |
|---|---|---|---|
| `internal/sim` | 86.4, 85.4, 85.3 s | 47.0, 47.0, 46.9 s | 55% |
| `internal/sqllogictest` | 49.8, 49.6, 49.5 s | 25.6, 25.3 s (after the review fixes; 30.1, 30.0, 30.1 s before them) | 51% |
| root | 41.1, 40.8, 41.0 s | 16.1, 13.0, 15.7 s | 36% |
| `internal/engine` | 33.2, 34.5, 33.9 s | 15.3, 14.2, 15.0 s | 44% |

Kill matrix: `make verification` with the change regenerated /internal/sim/testdata/kill-matrix.json, and its only diff from 020e781 is the line `"cannotSeeds": 5`. So every status, every first detecting seed, every checker list, and every reason is the same. `make report` after `make test` shows 145 of 224 configurations detected and 27 of 27 states reached by the corpus, as before.

### Why
The simulator was CPU-bound, so the only way down was fewer runs, and the runs that only confirm a "cannot" reason were 80% of the mutant runs. Seeds 1 to 5 still catch a reason that turns false early, and the soak and the verification run catch one that turns false later. The sqllogictest run was bound by one long file that waited on Postgres, so it needed that file split, not more CPU. The root and engine packages were serial for no reason.

### What worked
- `go test -json` plus a small Python summary showed the per-test times; `pprof -top -cum` showed where CPU went; `/usr/bin/time -p` showed CPU against wall time, which told CPU-bound from wait-bound at once.
- A per-file timing print, added to `runFiles` and removed again, showed `random/select` at 26 s of a 49 s run, and a print of slow Postgres statements showed the cross joins.
- `make verification` without `-race` runs the whole kill matrix in about 7 s, so checking the verdicts is cheap.
- Breaking the new code on purpose (no replay, no `break` at the first mismatch, no slots, merge in reverse, no transaction check) made the new tests fail every time.

### What didn't work
- A higher `GOGC` (400) cut `internal/sim` only from 83 s to 79 s, although the profile showed much runtime time (`runtime.madvise` 10%, `runtime.lock2` 15%); I did not keep it.
- More workers alone gave 35 s for sqllogictest: `random/select` slowed to about 33 s under the load and stayed the tail. Ordering by file size did not help either, because `random/select` is small (1.2 MB) for its cost.
- My first general sharding split a file anywhere and replayed every write before the shard. It cost more CPU (78 s against 63 s) and did not help `index/delete`, whose replay cost as much as the file. Shards of 1,000 or 500 were slower still (33 s, 39 s).
- A zsh loop with `set -- $cfg` did not split the words, so three timing runs used the wrong configuration and the helper failed with `IndexError: list index out of range`; `${=cfg}` fixed it.
- One mutation check copied its backup to a wrong path (`cp: ...run.go.shard: No such file or directory`) and left two mutations in /internal/sqllogictest/run.go; I found them with `grep` and reverted them by hand.

### What I learned
- The race detector makes the simulator about ten times slower: the full kill matrix takes 7 s without it and about 64 s with it at four CPUs.
- On this Mac, Postgres runs in Docker Desktop, and a write to its socket costs real CPU: `syscall.write` was 20% of the sqllogictest profile. CI runs Postgres as a Linux service container, so the wait there is smaller, but the package competes with the others for four CPUs.
- Another process on the machine (`swiftpm-testing-`, about 160% CPU) ran during all measurements. It was there for the before runs and the after runs alike, so the comparison holds, but the absolute numbers carry its noise.

### What was tricky
- The kill matrix had to stay identical cell by cell. Running fewer seeds only where a cell says it cannot detect the mutant keeps every detecting seed, because those cells still try up to 20.
- Shards must count like one sequence also after a mismatch, and the earliest mismatch must win; the first version added every shard's counts. A test that runs the same script with and without shards and compares the reports pins both.
- A shard must not run inside a transaction that the records before it left open; the runner checks for transaction statements statically instead of asking the session.
- An unbounded number of shards would open one Postgres connection each; the full corpus could pass Postgres's 100 connections.

### What warrants review
- The trade in `TestMutants`: a "cannot" reason that only a seed from 6 to 20 disproves now fails `make soak` and `make verification`, not `make test`. Check `allSeeds` and the soak line in /Makefile.
- `readOnly` in /internal/sqllogictest/run.go: it relies on maragudb rejecting every function that changes state, such as `nextval` (see /internal/sql/parser/parser.go), because a statement that maragudb rejects never runs on Postgres.
- `TestDB_Tigris` now runs in parallel with the other engine tests. It sizes its grace period and lease from measured latencies, and on CI it already ran next to other packages, but watch it for flakes.
- Validate with `make test`, `make verification` (no diff), and `make soak`. My `make soak` passed: the whole kill matrix in 6.5 s, 23,016 simulator runs in 5 minutes without anomalies, and the full corpus of 622 files in 8 m 36 s with sharding, with no file below its baseline.

### Future work
- Run the kill matrix without the race detector, in a child process, which would make it about ten times faster. It changes what CI checks, so it needs a decision.
- If `internal/sim` grows again, the corpus (298 runs) and the other simulator subtests are the next cost; they are about a quarter of its CPU.
