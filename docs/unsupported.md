# Unsupported Postgres SQL

maragudb accepts a strict subset of Postgres 18 SQL. Every statement that it accepts gives the same result as in Postgres, except for the differences that "Remaining differences" lists. When it cannot promise that, it rejects the statement with `maragudb.ErrUnsupported` (SQLSTATE 0A000, feature_not_supported) before it changes anything. The error message says what is unsupported and, where possible, what to write instead.

This document lists every class of statement that maragudb rejects, and the remaining differences from Postgres. Each class has a stable `UNS-` ID and its own test in `/internal/pgdiff/unsupported_test.go`. The test runs examples of the class on both databases. It asserts that Postgres accepts them and that maragudb rejects them, so the list cannot drift from the behavior.

The differential harness in `/internal/pgdiff` runs every generated statement on maragudb first. If maragudb rejects the statement, the harness skips it on Postgres and counts it as rejected. If not, the harness runs the same text on Postgres and compares the results.

## Features that maragudb does not have

- **The numeric type.** `UNS-NUMERIC` A numeric literal, such as `1.5`, `1e3`, or an integer beyond the bigint range, has type numeric in Postgres until its context converts it. maragudb supports the conversions to double precision, bigint, and text: `f + 1.5` on a double precision `f`, `1.5::float8`, an insert of `2.5` into a bigint column, and `'x' || 1.5`. Everywhere else, such as in `SELECT 1.5` or `1 + 1.5`, the result would be numeric, and maragudb rejects the statement. Write a cast, such as `1.5::float8`.
- **Other types.** `UNS-TYPES` The supported types are `bigint`, `double precision`, `boolean`, `text`, `bytea`, and `timestamptz`, with their aliases `int8`, `float8`, `float`, `bool`, and `timestamp with time zone`. Every other type name is rejected, among them `integer`, `smallint`, `real`, `numeric`, `varchar`, `date`, `timestamp`, `json`, and `uuid`, and so is a type modifier such as `timestamptz(3)`.
- **Timestamps outside ISO 8601 and the common era.** `UNS-TIMESTAMP-INPUT` maragudb reads a timestamptz in the ISO 8601 forms, such as `2024-01-02 03:04:05.123456+02` or `2024-01-02T03:04:05Z`, with or without a zone. It rejects the other forms that Postgres reads, such as `January 2, 2024`, special values such as `now` and `infinity`, named time zones such as `Europe/Oslo`, and instants before the year 1, which Postgres writes with a `BC` suffix.
- **Tables without a primary key.** `UNS-NO-PRIMARY-KEY` Every row lives at its primary key, so every table needs one. Add `PRIMARY KEY` to a column, or `PRIMARY KEY (columns)` to the table.
- **Other schema statements and constraints.** `UNS-DDL` The schema statements are `CREATE TABLE`, with `IF NOT EXISTS`, `DROP TABLE` of one table, with `IF EXISTS`, and `CREATE INDEX` and `DROP INDEX`, which the next entry describes. The constraints are `PRIMARY KEY`, `UNIQUE`, and `NOT NULL`. maragudb rejects the rest, such as `DEFAULT`, `CHECK`, `REFERENCES`, temporary tables, views, `ALTER TABLE`, `CASCADE`, and a `DROP TABLE` of several tables.
- **Other forms of indexes.** `UNS-INDEX` An index is `CREATE [UNIQUE] INDEX [IF NOT EXISTS] [name] ON table (column [ASC | DESC] [NULLS FIRST | LAST], ...) [NULLS [NOT] DISTINCT]`, and `DROP INDEX [IF EXISTS] name`. A `PRIMARY KEY` or `UNIQUE` constraint, with or without `CONSTRAINT name` and `NULLS [NOT] DISTINCT`, has an index too. Every index is a btree, and indexes and tables share one namespace, as in Postgres. maragudb rejects indexes on expressions, partial indexes with `WHERE`, `INCLUDE`, `USING`, `CONCURRENTLY`, `ON ONLY`, operator classes, `COLLATE`, storage parameters with `WITH`, `TABLESPACE`, `ALTER INDEX`, a `DROP INDEX` of several indexes, and the options `DEFERRABLE` and `NOT DEFERRABLE` of a constraint, which is always checked at once. Index the columns themselves, and leave the options out.
- **Other statements and transaction modes.** `UNS-STATEMENTS` The statements are `CREATE TABLE`, `DROP TABLE`, `INSERT`, `UPDATE`, `DELETE`, `SELECT`, and `BEGIN`, `START TRANSACTION`, `COMMIT`, `END`, `ROLLBACK`, and `ABORT`. Every transaction is serializable, so maragudb rejects other isolation levels and `DEFERRABLE`. It also rejects savepoints, `WITH`, `EXPLAIN`, `SET`, `TRUNCATE`, a bare `VALUES`, and the other Postgres statements, and a string with several statements.
- **Other clauses.** `UNS-CLAUSES` A `SELECT` reads one table, or none, with `WHERE`, `ORDER BY`, `LIMIT`, and `OFFSET`. maragudb rejects `DISTINCT`, `GROUP BY`, `HAVING`, joins, subqueries, `UNION` and the other set operations, table aliases, qualified names such as `t.c`, `FOR UPDATE`, `FETCH`, and a `SELECT` without output columns. In writes, it rejects `RETURNING`, `ON CONFLICT`, `INSERT ... SELECT`, `DEFAULT`, and `UPDATE ... FROM`.
- **Other functions.** `UNS-FUNCTIONS` The functions are `abs`, `coalesce`, `length`, `lower`, and `upper`. As in Postgres with the `C` locale, `lower` and `upper` change only ASCII letters. maragudb rejects every other function name, including the aggregates and window functions.
- **Other operators and predicates.** `UNS-OPERATORS` The operators are `+`, `-`, `*`, `/`, `%`, `||`, `=`, `<>`, `!=`, `<`, `<=`, `>`, `>=`, `AND`, `OR`, `NOT`, `IS NULL`, `IS NOT NULL`, `BETWEEN`, `IN` with a list, `LIKE`, `CASE`, and `CAST` with its `::` and `type 'text'` forms. maragudb rejects the rest, such as `IS DISTINCT FROM`, `IS TRUE`, `ILIKE`, regular expressions, bit operators, arrays, row constructors, `LIKE ... ESCAPE`, `LIKE` on bytea, `BETWEEN SYMMETRIC`, `COLLATE`, `AT TIME ZONE`, and the casts between bytea and integers that Postgres 18 added.
- **Other forms of constants and identifiers.** `UNS-LITERALS` Strings are written in standard quotes, where a backslash is an ordinary character. maragudb rejects escape strings such as `E'a\n'`, bit strings such as `B'101'` and `X'1F'`, national strings, Unicode escapes, dollar quoting, a string continued on the next line, and unquoted identifiers with letters outside ASCII. Bytes are written as text cast to bytea, such as `'\x01ff'::bytea`.

## Parameters

- **A parameter whose Go value would need a conversion.** `UNS-PARAMETERS` A parameter has no type of its own. As in Postgres, it takes the type its context gives it, the way a quoted literal does. A Go string is read exactly like a quoted literal, so `"5"` is the bigint 5 next to a bigint. An int64 is a bigint, an integer if it fits in 32 bits, or a double precision, and each other Go type is its own SQL type. Where the conversion is not one of these, such as a float64 used as a bigint, an int64 used as text, or a []byte used as a bigint, Postgres drivers differ in what they do, and maragudb rejects the statement. pgx, for one, sends a []byte for a bigint as text that the server then reads. Pass a value of the matching Go type, or cast the parameter, such as `$1::float8`.

## Statements whose outcome depends on Postgres's plan

Postgres decides some outcomes in its planner or by the physical order of rows, which maragudb cannot reproduce. A statement where that would show is rejected.

One plan choice maragudb does follow: with `enable_seqscan = off`, Postgres always scans an index when a condition of the `WHERE` clause can use one, and maragudb behaves as Postgres does with such a scan. The index conditions select the rows, and the other conditions are evaluated only on those rows, so `UPDATE acct SET b = b - $1 WHERE id = $2 AND b - $1 >= 0` never evaluates `b - $1` on another row. The index conditions are the conditions that cannot fail and are one of these, on any column of the primary key or of another index:

- a comparison with `=`, `<`, `<=`, `>`, or `>=` of the column with an expression that reads no columns, in the column's own type, such as `id = 5`, `5 < id`, or `id BETWEEN 1 AND 9`
- an `IN` of such expressions on the column, such as `id IN (1, 2)`
- a boolean column, or `NOT` of one
- an equality of the column with a constant that follows from the equalities of the clause, such as `id = 5` from `id = n AND n = 5`

Postgres puts every such condition into every scan of every index on its column. With several indexes, Postgres picks one scan by cost, so maragudb skips a row only when every scan that Postgres could pick skips it: every index that has index conditions rejects the row by one of them. An index without index conditions can still be scanned as a whole, when another condition could use it, such as an `OR`, a `LIKE`, or `IS NULL` on its column, when `ORDER BY` sorts by its first column, or when it has every column a `SELECT` reads. Then Postgres may read every row, and so does maragudb. On every row that some scan reads, a condition that fails on a row that another condition rejects is rejected as an outcome that depends on the order of the conditions. For example, with an index on `a`, `SELECT * FROM t WHERE id = 1 AND a = 2 AND 10 / j > 0` is rejected when `j` is 0 on a row where `a` is 2, because Postgres may scan either index. Other conditions on indexed columns, such as an `OR` of comparisons, a `LIKE`, `<>`, or a column in an expression or cast to another type, are evaluated on every row that the index conditions select, as in Postgres's plan they may be. Postgres in its default configuration can also scan the whole table, which DEV-20 describes.

- **LIMIT and OFFSET without a total order.** `UNS-LIMIT-ORDER` Which rows Postgres returns under `LIMIT` or `OFFSET` depends on its plan unless `ORDER BY` sorts by every primary key column. Add the primary key columns to `ORDER BY`.
- **LIMIT and OFFSET with an expression that can fail.** `UNS-PLAN-DEPENDENT-LIMIT` Under a `LIMIT`, an index scan stops early and a sequential scan with a sort does not, so how many rows Postgres evaluates an expression on depends on its plan. maragudb rejects `LIMIT` and `OFFSET` when an output, `ORDER BY`, or `WHERE` expression can fail at run time, such as an addition, which can overflow, or a cast of text. Select the rows first, and compute the expression on the result.
- **A LIKE on an indexed column whose pattern can fail.** `UNS-PLAN-DEPENDENT-WHERE` For a `LIKE` on a column of the primary key or of another index with a constant pattern, Postgres scans the index for the range of the pattern's fixed prefix, or for one value when the pattern has no wildcard, and evaluates the `LIKE` only on those rows. When the pattern can fail, such as `s LIKE 'b\'`, which ends in its escape character, which rows it fails on depends on that range. maragudb rejects such a `LIKE`. Write the pattern without a trailing escape character.

- **A condition that fails on a row that another condition rejects.** `UNS-ORDER-DEPENDENT-WHERE` Postgres evaluates the conditions of a `WHERE` clause in an order its planner picks and stops at the first that is not true. When one condition fails on a row that another rejects, such as `m <> 0 AND 10 / m > 1` on a row where `m` is 0, whether the statement fails depends on that order, as the Postgres documentation warns. maragudb evaluates every condition that can fail on such a row, and rejects the statement when the outcome would depend on the order. It considers the equalities that Postgres derives from the written ones too. The statement still fails with the row's own error when every order fails. Write `CASE WHEN m <> 0 THEN 10 / m > 1 END` to fix the order.
- **A conversion between text and timestamptz that reads no columns and can fail.** `UNS-STABLE-CONSTANT` Postgres does not fold a conversion between timestamptz and text into a constant, because it depends on the session's time zone. It evaluates such an expression when the statement runs, but also while it plans, to estimate how many rows a condition matches, depending on where the expression is. When the expression can fail, such as `CAST(CAST('2024-01-02' AS text) AS timestamptz)`, whether the statement fails depends on the plan. Write the timestamptz as a quoted literal, such as `'2024-01-02 00:00:00+00'`.
- **An UPDATE that moves a row onto a key that another row leaves.** `UNS-KEY-UPDATE-ORDER` Postgres checks the primary key and every unique index of each row as it updates it, in the order it visits the rows, so `UPDATE t SET id = id + 1` and, with a unique index on `j`, `UPDATE t SET j = j + 1` succeed or fail depending on that order. The Postgres documentation says so for constraints that are not deferrable. maragudb computes every new key first. When the rows that move onto keys that other rows of the statement leave form a cycle, such as two rows that swap their keys, every order fails, and so does maragudb. When they only form chains, it rejects the statement. Otherwise it succeeds or fails exactly as Postgres does in every order. Update such rows in two statements.

## Errors that depend on order

When different rows of a statement fail for different reasons, Postgres reports the error of the row it reaches first, which depends on the physical order of the rows, or on the order of an index it scans. maragudb visits rows in primary key order, also when it finds them through another index. Both fail, but the error class may differ. The differential harness accepts a different class only when Postgres, given the rows stored in key order and with its other indexes set aside, reports the same class as maragudb. Postgres then scans the table or its primary key, which is one of the plans it can pick, and maragudb fails for certain only on a row that every plan reads.

An INSERT checks its rows in the order it lists them, as Postgres does, and so reports the same row's error.

## Remaining differences

For the statements it accepts, maragudb has one known difference from Postgres. It has a `DEV-` ID and its own test in `/internal/pgdiff/unsupported_test.go`, which runs the example on both databases.

- **A condition that can fail on a row that the primary key does not select.** `DEV-20` maragudb evaluates the conditions of a `WHERE` clause only on the rows that its primary key conditions select, as Postgres does when it scans the primary key index. Postgres in its default configuration can scan the whole table instead, for example when the table is small, and then it evaluates the conditions on every row. When a condition fails on a row that the key does not select, Postgres fails and maragudb does not. On a table `acct` with the rows `(1, 100)`, `(2, 50)`, and `(9, -9223372036854775808)`, after `ANALYZE`, Postgres fails `UPDATE acct SET b = b - 10 WHERE id IN (1, 2, 3, 4, 5) AND b - 10 >= 0` with bigint out of range on the row 9, and maragudb updates the rows 1 and 2. With `enable_seqscan = off`, Postgres updates the rows 1 and 2 too. The differential harnesses run Postgres with that setting. So here maragudb is more lenient than Postgres.

The deviations of the former own SQL flavor, DEV-1 to DEV-19 in its deviations document, are gone, and their IDs are not reused:

| Former deviation | Now |
|---|---|
| DEV-1, no implicit coercion between integers and floats | eliminated: Postgres's implicit casts |
| DEV-2, no assignment casts | eliminated: Postgres's assignment casts |
| DEV-3, parameters never adapt | eliminated, except UNS-PARAMETERS |
| DEV-4, `\|\|` only for two strings or two bytes | eliminated: text with any type |
| DEV-5, LIMIT and OFFSET only take an integer | eliminated: Postgres's conversion to bigint |
| DEV-6, integer literals must fit in 64 bits | UNS-NUMERIC |
| DEV-7, nanosecond times | eliminated: microseconds, rounded as in Postgres |
| DEV-8, RFC 3339 time casts | eliminated: Postgres's output format, and UNS-TIMESTAMP-INPUT |
| DEV-9, bytes cast as UTF-8 | eliminated: Postgres's hex and escape formats |
| DEV-10, decimal-only number casts | eliminated: Postgres's input formats |
| DEV-11, Unicode case folding | eliminated: ASCII only, as with the `C` locale |
| DEV-12, a failed statement keeps the transaction usable | eliminated: the transaction is aborted until it ends |
| DEV-13, rows visited in key order | UNS-KEY-UPDATE-ORDER, and errors that depend on order |
| DEV-14, every table needs a primary key | UNS-NO-PRIMARY-KEY |
| DEV-15, more reserved words | eliminated: Postgres's reserved words |
| DEV-16, output names of casts | eliminated: Postgres's names, such as `int8` |
| DEV-17, a string literal is a string | eliminated: a quoted literal takes the type of its context |
| DEV-18, LIKE on a primary key column | UNS-PLAN-DEPENDENT-WHERE |
| DEV-19, WHERE conjuncts in written order | UNS-ORDER-DEPENDENT-WHERE |
