# Unsupported Postgres SQL

maragudb accepts a strict subset of Postgres 18 SQL. Every statement that it accepts gives the same result as in Postgres, except for the differences that "Remaining differences" lists. When it cannot promise that, it rejects the statement with `maragudb.ErrUnsupported` (SQLSTATE 0A000, feature_not_supported) before it changes anything. The error message says what is unsupported and, where possible, what to write instead.

This document lists every class of statement that maragudb rejects, and the remaining differences from Postgres. Each class has a stable `UNS-` ID and its own test in `/internal/pgdiff/unsupported_test.go`. The test runs examples of the class on both databases. It asserts that Postgres accepts them and that maragudb rejects them, so the list cannot drift from the behavior.

The differential harness in `/internal/pgdiff` runs every generated statement on maragudb first. If maragudb rejects the statement, the harness skips it on Postgres and counts it as rejected. If not, the harness runs the same text on Postgres and compares the results.

## Features that maragudb does not have

- **The numeric type.** `UNS-NUMERIC` A numeric literal, such as `1.5`, `1e3`, or an integer beyond the bigint range, has type numeric in Postgres until its context converts it. maragudb supports the conversions to double precision, bigint, and text: `f + 1.5` on a double precision `f`, `1.5::float8`, an insert of `2.5` into a bigint column, and `'x' || 1.5`. Everywhere else, such as in `SELECT 1.5` or `1 + 1.5`, the result would be numeric, and maragudb rejects the statement. Write a cast, such as `1.5::float8`. A value of type numeric exists only as the result of `SUM` of bigint and of `AVG` of integer and bigint, and of arithmetic on those results, which the numeric decisions of 2026-11-06 describe. Such a value compares with another, with integers and bigints, and with double precision, through Postgres's implicit casts, and works in `ORDER BY`, `DISTINCT`, `IS NULL`, `CASE`, `COALESCE`, `NULLIF`, and `||`, and in casts to bigint, double precision, and text. It also works in arithmetic: unary `-` and `+`, and `+`, `-`, `*`, `/`, and `%` with another numeric, an integer, or a bigint, such as `-SUM(x)`, `SUM(a) + SUM(b)`, `SUM(x) / 2`, and `AVG(x) * COUNT(*)`, with Postgres's scale rules and errors. With a double precision operand the result is double precision, as in Postgres. maragudb rejects every function of a numeric, such as `abs(AVG(x))` or `round`, an aggregate over a numeric, a numeric literal next to it, such as `SUM(x) * 1.5` or `AVG(x) > 1.5`, and a quoted literal that Postgres would read as numeric, such as `SUM(x) = '5'` or `AVG(x) * 2 > '5'`. Cast the result, such as `SUM(x)::bigint` or `AVG(x)::float8`, or cast the literal, such as `'5'::bigint` or `1.5::float8`. Numeric columns and casts to numeric are rejected by their type name, under UNS-TYPES.
- **Other types.** `UNS-TYPES` The supported types are `bigint`, `double precision`, `boolean`, `text`, `bytea`, and `timestamptz`, with their aliases `int8`, `float8`, `float`, `bool`, and `timestamp with time zone`. Every other type name is rejected, among them `integer`, `smallint`, `real`, `numeric`, `varchar`, `date`, `timestamp`, `json`, and `uuid`, and so is a type modifier such as `timestamptz(3)`.
- **Timestamps outside ISO 8601 and the common era.** `UNS-TIMESTAMP-INPUT` maragudb reads a timestamptz in the ISO 8601 forms, such as `2024-01-02 03:04:05.123456+02` or `2024-01-02T03:04:05Z`, with or without a zone. It rejects the other forms that Postgres reads, such as `January 2, 2024`, special values such as `now` and `infinity`, named time zones such as `Europe/Oslo`, and instants before the year 1, which Postgres writes with a `BC` suffix.
- **Tables without a primary key.** `UNS-NO-PRIMARY-KEY` Every row lives at its primary key, so every table needs one. Add `PRIMARY KEY` to a column, or `PRIMARY KEY (columns)` to the table.
- **Other schema statements and constraints.** `UNS-DDL` The schema statements are `CREATE TABLE`, with `IF NOT EXISTS`, `DROP TABLE` of one table, with `IF EXISTS`, and `CREATE INDEX` and `DROP INDEX`, which the next entry describes. The constraints are `PRIMARY KEY`, `UNIQUE`, `NOT NULL`, `DEFAULT`, `CHECK`, and `FOREIGN KEY` or `REFERENCES`, with the limits that the entries below describe. maragudb rejects the rest, such as `EXCLUDE`, a name for a `NOT NULL` constraint, temporary tables, views, `ALTER TABLE`, `CASCADE`, and a `DROP TABLE` of several tables.
- **Sequences.** `UNS-SEQUENCES` maragudb has no sequences, because a counter that many writers share is a design of its own. It rejects `CREATE SEQUENCE`, the types `serial`, `bigserial`, and `smallserial`, identity columns with `GENERATED ... AS IDENTITY`, and the functions `nextval`, `currval`, `setval`, and `lastval`. Use `bigint` and generate the keys in the application.
- **A DEFAULT that can fail.** `UNS-DEFAULT` A `DEFAULT` is a constant, or an expression with `now()` and its synonyms. Postgres evaluates the constant parts of a default only in the statement that uses it, so a default such as `1 / 0` fails that statement, in an order among its other errors that maragudb does not reproduce. maragudb rejects such a default when the table is created, and also a default that can fail when it is evaluated, such as `CAST(CAST(now() AS text) AS timestamptz)`. Write a default that cannot fail.
- **Other forms of CHECK.** `UNS-CHECK` A `CHECK` constraint, of a column or of the table, is a boolean expression over the table's columns, with `CONSTRAINT name` or the name Postgres chooses. maragudb checks it on every row that an `INSERT` or `UPDATE` writes, in the order of the names, after `NOT NULL` and before the keys, as Postgres does. It rejects `NO INHERIT`, `NOT VALID`, and `NOT ENFORCED`, and a `CHECK` whose constant part fails, such as `CHECK (1 / 0 > 0)`, which Postgres folds only when it checks the first row.
- **Other forms of FOREIGN KEY.** `UNS-FOREIGN-KEY` A foreign key, `REFERENCES` on a column or `FOREIGN KEY` on the table, references the primary key of a table, or columns of it that have a primary key or a unique index, and is `MATCH SIMPLE`: a row with a NULL in its key is not checked. maragudb checks it at the end of each statement and fires `ON DELETE` `NO ACTION`, `RESTRICT`, `CASCADE`, `SET NULL`, and `SET DEFAULT`, with a list of columns or without, and `ON UPDATE` `NO ACTION` and `RESTRICT`, in the order Postgres fires them. It rejects `MATCH FULL` and `MATCH PARTIAL`, `ON UPDATE CASCADE`, `SET NULL`, and `SET DEFAULT`, `NOT VALID`, `NOT ENFORCED`, `DEFERRABLE`, and a foreign key on double precision columns, or from a bigint to a double precision, because which values Postgres finds equal then depends on how it compares them. Update the referencing rows in a statement of their own, and reference bigint or text columns.
- **Other forms of indexes.** `UNS-INDEX` An index is `CREATE [UNIQUE] INDEX [IF NOT EXISTS] [name] ON table (column [ASC | DESC] [NULLS FIRST | LAST], ...) [NULLS [NOT] DISTINCT]`, and `DROP INDEX [IF EXISTS] name`. A `PRIMARY KEY` or `UNIQUE` constraint, with or without `CONSTRAINT name` and `NULLS [NOT] DISTINCT`, has an index too. Every index is a btree, and indexes and tables share one namespace, as in Postgres. maragudb rejects indexes on expressions, partial indexes with `WHERE`, `INCLUDE`, `USING`, `CONCURRENTLY`, `ON ONLY`, operator classes, `COLLATE`, storage parameters with `WITH`, `TABLESPACE`, `ALTER INDEX`, a `DROP INDEX` of several indexes, and the options `DEFERRABLE` and `NOT DEFERRABLE` of a constraint, which is always checked at once. Index the columns themselves, and leave the options out.
- **Other statements and transaction modes.** `UNS-STATEMENTS` The statements are `CREATE TABLE`, `DROP TABLE`, `INSERT`, `UPDATE`, `DELETE`, `SELECT`, and `BEGIN`, `START TRANSACTION`, `COMMIT`, `END`, `ROLLBACK`, and `ABORT`. Every transaction is serializable, so maragudb rejects other isolation levels and `DEFERRABLE`. It also rejects savepoints, `EXPLAIN`, `SET`, `TRUNCATE`, a bare `VALUES`, and the other Postgres statements, and a string with several statements.
- **Other clauses.** `UNS-CLAUSES` A `SELECT` reads the tables of its `FROM`, or none, with `WITH`, `DISTINCT`, `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY`, `LIMIT`, and `OFFSET`, and its expressions can have subqueries, which the next entries describe. maragudb rejects `DISTINCT ON`, `UNION` and the other set operations, also in a subquery, `FOR UPDATE`, `FETCH`, and a `SELECT` without output columns. In writes, it rejects `RETURNING`, `ON CONFLICT`, `INSERT ... SELECT`, an alias in `INSERT`, `UPDATE ... FROM`, and `DELETE ... USING`. Read the other tables in a `SELECT` first.
- **Other forms of FROM and of names.** `UNS-JOINS` The items of `FROM` are tables, with an alias with or without `AS` and names for their first columns, such as `t AS x (a, b)`, and joins of them: several items separated by commas, `CROSS JOIN`, `[INNER] JOIN` and `LEFT [OUTER] JOIN` with `ON`, with `USING`, or `NATURAL`, in parentheses and nested in any way, subqueries with an alias, such as `(SELECT a FROM t) AS x (b)`, and the queries of `WITH`. A column is named alone or qualified by the alias or name of its table, such as `x.a`, and `x.*` selects every column of a table. `UPDATE` and `DELETE` take an alias too. maragudb rejects `RIGHT` and `FULL` joins, `LATERAL`, an alias for a join in parentheses or for the columns of `USING`, `VALUES` and functions in `FROM`, `ONLY`, `TABLESAMPLE`, names with a schema, such as `public.t` or `s.t.c`, a reference to a whole row, such as `SELECT t FROM t` or `t.*` in an expression, the same name twice in the names of the columns of a table, and more than 64 tables in a statement. Write a `LEFT JOIN` with the tables the other way round, and name the columns.
- **Other forms of subqueries and of WITH.** `UNS-SUBQUERIES` maragudb supports `x [NOT] IN (SELECT ...)`, `[NOT] EXISTS (SELECT ...)`, and scalar subqueries, correlated with the queries around them or not, at any depth, in the output, `WHERE`, the conditions of joins, `HAVING`, and `ORDER BY` of a `SELECT`, in the `WHERE` and `SET` of `UPDATE`, in the `WHERE` of `DELETE`, and in the `VALUES` of `INSERT`. A subquery in a write reads the rows as the statement began, also of the table it writes. It also supports subqueries in `FROM` with an alias, and a `WITH` of several queries in front of a `SELECT` or inside a subquery, with names for their columns, each reading the ones before it, read several times or never. maragudb rejects `ANY`, `SOME`, and `ALL`, a row on the left of `IN`, such as `(a, b) IN (SELECT ...)`, `WITH RECURSIVE`, `MATERIALIZED` and `NOT MATERIALIZED`, a query that writes in `WITH`, `WITH` in front of `INSERT`, `UPDATE`, or `DELETE`, a subquery in `FROM` without an alias, an aggregate of the columns of a query around its subquery, such as `SELECT (SELECT sum(t.x)) FROM t`, `t.*` of a table of a query around a subquery, and a subquery in the list of an `IN`, in `GROUP BY`, or in `LIMIT` or `OFFSET`. Write `IN` instead of `= ANY`, give the subquery an alias, compute the aggregate in the query around, and run the queries of a `WITH` before the write.
- **Other aggregates and forms of grouping.** `UNS-AGGREGATES` The aggregates are `count`, `sum`, `avg`, `min`, and `max`, with or without `DISTINCT`, and `GROUP BY` groups by expressions, or by the position or name of an output column. maragudb rejects `FILTER`, `ORDER BY` in the arguments of an aggregate, `WITHIN GROUP`, `GROUPING SETS`, `ROLLUP`, `CUBE`, the empty grouping set `()`, `GROUP BY ALL` and `GROUP BY DISTINCT`, `GROUPING()`, and every other aggregate function, such as `string_agg`, `array_agg`, `bool_and`, `bool_or`, and `every`. It also rejects a parameter as the argument of an aggregate, such as `sum($1)`, because the parameter's type is unknown; cast it, such as `sum($1::bigint)`. `MIN` and `MAX` of a boolean fail with SQLSTATE 42883, as in Postgres, which has no `min(boolean)`.
- **Other functions.** `UNS-FUNCTIONS` The functions are `abs`, `coalesce`, `length`, `lower`, `nullif`, `upper`, and `now`, with its synonyms `transaction_timestamp()` and `CURRENT_TIMESTAMP`, and the aggregates `count`, `sum`, `avg`, `min`, and `max`. As in Postgres with the `C` locale, `lower` and `upper` change only ASCII letters. `now()` is the start of the transaction, the same value for every use in one transaction, at microsecond precision. maragudb rejects every other function name, including window functions with `OVER`, and the other clocks: `statement_timestamp()`, `clock_timestamp()`, `timeofday()`, `CURRENT_TIMESTAMP` with a precision, and `LOCALTIMESTAMP`, `CURRENT_DATE`, `CURRENT_TIME`, and `LOCALTIME`, whose types maragudb does not have. Write `now()`.
- **Other operators and predicates.** `UNS-OPERATORS` The operators are `+`, `-`, `*`, `/`, `%`, `||`, `=`, `<>`, `!=`, `<`, `<=`, `>`, `>=`, `AND`, `OR`, `NOT`, `IS NULL`, `IS NOT NULL`, `BETWEEN`, `IN` with a list, `LIKE`, `CASE`, and `CAST` with its `::` and `type 'text'` forms. maragudb rejects the rest, such as `IS DISTINCT FROM`, `IS TRUE`, `ILIKE`, regular expressions, bit operators, arrays, row constructors, `LIKE ... ESCAPE`, `LIKE` on bytea, `BETWEEN SYMMETRIC`, `COLLATE`, `AT TIME ZONE`, and the casts between bytea and integers that Postgres 18 added.
- **Other forms of constants and identifiers.** `UNS-LITERALS` Strings are written in standard quotes, where a backslash is an ordinary character. maragudb rejects escape strings such as `E'a\n'`, bit strings such as `B'101'` and `X'1F'`, national strings, Unicode escapes, dollar quoting, a string continued on the next line, and unquoted identifiers with letters outside ASCII. Bytes are written as text cast to bytea, such as `'\x01ff'::bytea`.

## Parameters

- **A parameter whose Go value would need a conversion.** `UNS-PARAMETERS` A parameter has no type of its own. As in Postgres, it takes the type its context gives it, the way a quoted literal does. A Go string is read exactly like a quoted literal, so `"5"` is the bigint 5 next to a bigint. An int64 is a bigint, an integer if it fits in 32 bits, or a double precision, and each other Go type is its own SQL type. Where the conversion is not one of these, such as a float64 used as a bigint, an int64 used as text, or a []byte used as a bigint, Postgres drivers differ in what they do, and maragudb rejects the statement. pgx, for one, sends a []byte for a bigint as text that the server then reads. Pass a value of the matching Go type, or cast the parameter, such as `$1::float8`.

## Statements whose outcome depends on Postgres's plan

Postgres decides some outcomes in its planner or by the physical order of rows, which maragudb cannot reproduce. A statement where that would show is rejected.

One plan choice maragudb does follow: with `enable_seqscan = off`, Postgres always scans an index when a condition of the `WHERE` clause can use one, and maragudb behaves as Postgres does with such a scan. The index conditions select the rows, and the other conditions are evaluated only on those rows, so `UPDATE acct SET b = b - $1 WHERE id = $2 AND b - $1 >= 0` never evaluates `b - $1` on another row. The index conditions are the conditions that cannot fail and are one of these, on any column of the primary key or of another index:

- a comparison with `=`, `<`, `<=`, `>`, or `>=` of the column with an expression that reads no columns, in the column's own type, such as `id = 5`, `5 < id`, or `id BETWEEN 1 AND 9`
- an `IN` of such expressions on the column, such as `id IN (1, 2)`
- a boolean column, or `NOT` of one
- an equality of the column with a constant that follows from the equalities of the clause, such as `id = 5` from `id = n AND n = 5`

Postgres puts every such condition into every scan of every index on its column. With several indexes, Postgres picks one scan by cost, so maragudb skips a row only when every scan that Postgres could pick skips it: every index that has index conditions rejects the row by one of them. An index without index conditions can still be scanned as a whole, when another condition could use it, such as an `OR`, a `LIKE`, or `IS NULL` on its column, when `ORDER BY` sorts by its first column, or when it has every column a `SELECT` reads. Then Postgres may read every row, and so does maragudb. On every row that some scan reads, a condition that fails on a row that another condition rejects is rejected as an outcome that depends on the order of the conditions. For example, with an index on `a`, `SELECT * FROM t WHERE id = 1 AND a = 2 AND 10 / j > 0` is rejected when `j` is 0 on a row where `a` is 2, because Postgres may scan either index. Other conditions on indexed columns, such as an `OR` of comparisons, a `LIKE`, `<>`, or a column in an expression or cast to another type, are evaluated on every row that the index conditions select, as in Postgres's plan they may be. Postgres in its default configuration can also scan the whole table, which DEV-20 describes.

- **LIMIT and OFFSET without a total order.** `UNS-LIMIT-ORDER` Which rows Postgres returns under `LIMIT` or `OFFSET` depends on its plan unless `ORDER BY` sorts by every primary key column, of every table of a join, or, with `DISTINCT`, by every output column. A grouped `SELECT` with `GROUP BY` needs an `ORDER BY` on every `GROUP BY` expression: the same expression, or the position or name of the output column that is it. Without `GROUP BY`, a grouped `SELECT` has one row at most and needs no `ORDER BY`. Add the primary key columns, or the `GROUP BY` expressions, to `ORDER BY`.
- **LIMIT and OFFSET with an expression that can fail.** `UNS-PLAN-DEPENDENT-LIMIT` Under a `LIMIT`, an index scan stops early and a sequential scan with a sort does not, so how many rows Postgres evaluates an expression on depends on its plan. maragudb rejects `LIMIT` and `OFFSET` when an output, `ORDER BY`, or `WHERE` expression can fail at run time, such as an addition, which can overflow, or a cast of text. On a grouped `SELECT` with `GROUP BY`, sorted grouping under a `LIMIT` stops reading rows once it has enough groups, as `EXPLAIN` shows with a `Limit` over a `GroupAggregate` over an index scan, so maragudb also rejects `LIMIT` and `OFFSET` when a `GROUP BY` expression, an argument of an aggregate, a `SUM` or `AVG` of double precision, or a `HAVING` condition can fail. Select the rows first, and compute the expression on the result.
- **A SUM or AVG of double precision whose result depends on the order of the rows.** `UNS-FLOAT-SUM` Postgres adds the values of `SUM` and `AVG` of double precision in the order its plan reads the rows, with `float8pl` for `SUM` and `float8_accum` for `AVG`. Floating-point addition depends on that order, and so does whether it overflows, which is an error (SQLSTATE 22003). maragudb accepts such a `SUM` or `AVG` only when every order gives the same result: when every value and every sum of some of them is exact, that is, when the values are multiples of the smallest power of two among their lowest set bits and the sum of their magnitudes in that unit is at most 2^53, such as integers or quarters of moderate size. NaN and the infinities give NaN or an infinity in every order when the finite values cannot overflow. `AVG` also adds the squares of the deviations, which can overflow on their own, as Postgres fails `avg` of 1e200 and -1e200, so maragudb rejects an `AVG` whose squares could overflow. Otherwise it rejects the statement, such as `SELECT sum(f) FROM t` over 0.1, 0.2, and 0.3. Sum integers, or cast the values to bigint.
- **MIN and MAX that Postgres computes from the first row of an index, with a WHERE condition that fails.** `UNS-PLAN-DEPENDENT-AGGREGATE` A `SELECT` on one table without `GROUP BY` whose aggregates are all `MIN` and `MAX` can be computed by Postgres from the first row of an index that passes the `WHERE` clause, as `EXPLAIN` shows with an `InitPlan` with a `Limit` and an index scan, so it reads no other rows. A `WHERE` condition that fails on another row then fails or not depending on the plan: `SELECT min(id) FROM t WHERE 10 / x > 0` succeeds when the first row passes, while `SELECT min(id), count(*) FROM t WHERE 10 / x > 0` fails. maragudb rejects such a statement when a `WHERE` condition fails on a row. Write the condition so that it cannot fail, such as with `CASE`.
- **A LIKE on an indexed column whose pattern can fail.** `UNS-PLAN-DEPENDENT-WHERE` For a `LIKE` on a column of the primary key or of another index with a constant pattern, Postgres scans the index for the range of the pattern's fixed prefix, or for one value when the pattern has no wildcard, and evaluates the `LIKE` only on those rows. When the pattern can fail, such as `s LIKE 'b\'`, which ends in its escape character, which rows it fails on depends on that range. maragudb rejects such a `LIKE`. Write the pattern without a trailing escape character.

- **A condition that fails on a row that another condition rejects.** `UNS-ORDER-DEPENDENT-WHERE` Postgres evaluates the conditions of a `WHERE` clause in an order its planner picks and stops at the first that is not true. When one condition fails on a row that another rejects, such as `m <> 0 AND 10 / m > 1` on a row where `m` is 0, whether the statement fails depends on that order, as the Postgres documentation warns. maragudb evaluates every condition that can fail on such a row, and rejects the statement when the outcome would depend on the order. It considers the equalities that Postgres derives from the written ones too. The statement still fails with the row's own error when every order fails. The same applies to `HAVING`. Postgres moves each conjunct of `HAVING` without an aggregate, after it folds constants, into `WHERE`, where the rules of `WHERE` apply to it; with `GROUP BY` the conjunct moves, and without `GROUP BY` it also stays in `HAVING`. The conjuncts that keep an aggregate are evaluated on every group in an order Postgres picks, so a condition that fails on a group that another condition rejects is rejected too, such as `HAVING count(*) > 1 AND 10 / (count(*) - 1) > 0` on a group of one row. Write `CASE WHEN m <> 0 THEN 10 / m > 1 END` to fix the order.
- **A condition of a join that fails on a row that some plan evaluates it on.** `UNS-PLAN-DEPENDENT-JOIN` Postgres chooses the order of the joins of a `SELECT` on several tables, and the method of each, a nested loop, a hash join, or a merge join, by cost, and pushes each condition down to the lowest place where it can evaluate it, a condition on one table into the scan of that table. Which rows and pairs of rows it evaluates a condition on therefore depends on the plan. A hash join evaluates the other conditions of a join only on the pairs whose keys are equal, a nested loop with an index scan only on the rows that the index finds, a merge join stops when either side ends, and a join with an empty side may never scan the other side. So when a condition of `WHERE` or `ON` fails on one row, whether the statement fails depends on the plan. maragudb evaluates every condition that can fail on every row and combination of rows that a plan of Postgres could evaluate it on: the rows that the scans of its tables could read, as for one table, with NULLs for a table that a `LEFT JOIN` can extend with NULLs, and also each side of a comparison alone, which Postgres evaluates as the key of a hash join or a merge join or as the value of an index scan, and the conditions that it takes out of an `OR` for the scan of one table. It rejects the statement when one of them fails, and also when they are more than 100,000. For example, `SELECT * FROM a JOIN b ON a.id = b.aid WHERE 10 / b.w > 0` is rejected when a row of `b` has `w` 0, also when no row of `a` matches it. Write the condition so that it cannot fail, such as with `CASE WHEN b.w <> 0 THEN 10 / b.w > 0 END`, or compute the expression in the output, which Postgres evaluates only on the rows of the result.
- **A subquery whose evaluation fails where one plan evaluates it and another does not.** `UNS-PLAN-DEPENDENT-SUBQUERY` Postgres evaluates an uncorrelated subquery once, lazily when an expression first needs it, before a scan when it is the value of an index condition, also of an empty table, or never; it turns `IN`, also correlated, and `EXISTS` into semi-joins and `NOT EXISTS` into an anti-join, which evaluate the conditions of the subquery on its rows also when no row of the query around reaches them; it evaluates `IN` and `NOT IN` as hashed subplans; a subplan stops at the first row that decides it, and a scalar subquery at its second row; `EXISTS` drops the output of its query; and Postgres merges a subquery in `FROM`, and a CTE that is read once, into the query around, where it evaluates their conditions and the conditions of the query around in an order and through scans that it picks, while it evaluates a CTE that is read twice as a whole and one that is never read not at all. So whether a subquery that can fail fails depends on the plan. maragudb evaluates every subquery completely, and rejects the statement when that evaluation fails: an uncorrelated subquery in `WHERE`, `ON`, or `HAVING` is evaluated before any row is read, a correlated `EXISTS` that can fail also with NULL for every column of the query around, so that its conditions are evaluated on every row its scans could read, and a subquery in `FROM` or a CTE before the statement reads any row. It also rejects a correlated `IN` in a condition whose subquery can fail, a condition that reads a column of a subquery in `FROM` or a CTE when the condition or that query can fail, and a statement that evaluates its subqueries more than 20,000 times. Where the statement around evaluates a subquery follows the plan rules of that statement, for which a subquery that can fail is an expression that can fail, so a scalar subquery with more than one row fails with SQLSTATE 21000 where every plan evaluates it, such as in the output. For example, `SELECT * FROM t WHERE a = (SELECT b FROM u)` is rejected when `u` has two rows, because Postgres fails when it evaluates the subquery for an index scan and succeeds when no row of `t` reaches it. Write the subquery so that it cannot fail, such as with `CASE`, or with an aggregate that has one row.
- **DISTINCT, GROUP BY, MIN, and MAX of values that are equal but print differently.** `UNS-DISTINCT-ZERO` `SELECT DISTINCT` keeps one row of every group of equal rows, and which row of the group Postgres outputs depends on its plan. The double precision values -0 and 0 are equal but print differently, and so are numerics of different scales, such as `1` and `1.00000000000000000000`, which one column can hold through `CASE` or `COALESCE` of `SUM` and `AVG`, or through arithmetic on them, such as `AVG(x) * 0`. maragudb rejects a `SELECT DISTINCT` whose result has a group with both of them in one column. For the same reason it rejects a `GROUP BY` whose group has both -0 and 0 when the query reads the group's value, because which row's value Postgres keeps depends on its plan; a `MIN` or `MAX` of double precision whose result is zero when both -0 and 0 are among the values, because Postgres's `float8smaller` and `float8larger` keep the later of two equal values; and a `SUM(DISTINCT)` of -0 and 0. Add 0 to the expression, which makes -0 into 0.
- **A conversion between text and timestamptz that reads no columns and can fail.** `UNS-STABLE-CONSTANT` Postgres does not fold a conversion between timestamptz and text into a constant, because it depends on the session's time zone. It evaluates such an expression when the statement runs, but also while it plans, to estimate how many rows a condition matches, depending on where the expression is. When the expression can fail, such as `CAST(CAST('2024-01-02' AS text) AS timestamptz)`, whether the statement fails depends on the plan. Write the timestamptz as a quoted literal, such as `'2024-01-02 00:00:00+00'`.
- **Foreign key actions whose outcome depends on their order.** `UNS-FOREIGN-KEY-ORDER` Postgres fires the actions and checks of foreign keys as triggers at the end of a statement: for each row in the order it visits them, and for each row in the order of the triggers' names, which follows the creation order of the foreign keys only while their object identifiers have the same number of digits. When an action writes columns that another action or a check reads, the outcome can depend on that order. For example, with a table `c` that references `p` twice, by `x` with `NO ACTION` and by `y` with `ON DELETE CASCADE`, deleting a row of `p` that one row of `c` references by both fails or succeeds depending on which trigger fires first. maragudb rejects a `DELETE` whose actions could write columns that a `NO ACTION` or `RESTRICT` check, or the check of a foreign key of a row that `SET NULL` or `SET DEFAULT` changed, reads, or whose actions could write one table through more than one foreign key, unless they only delete rows. Give the tables that the actions change no other foreign key that acts on them or checks them.
- **An UPDATE that moves a row onto a key that another row leaves.** `UNS-KEY-UPDATE-ORDER` Postgres checks the primary key and every unique index of each row as it updates it, in the order it visits the rows, so `UPDATE t SET id = id + 1` and, with a unique index on `j`, `UPDATE t SET j = j + 1` succeed or fail depending on that order. The Postgres documentation says so for constraints that are not deferrable. maragudb computes every new key first. When the rows that move onto keys that other rows of the statement leave form a cycle, such as two rows that swap their keys, every order fails, and so does maragudb. When they only form chains, it rejects the statement. Otherwise it succeeds or fails exactly as Postgres does in every order. Update such rows in two statements.

## Errors that depend on order

When different rows of a statement fail for different reasons, Postgres reports the error of the row it reaches first, which depends on the physical order of the rows, or on the order of an index it scans. maragudb visits rows in primary key order, also when it finds them through another index. Both fail, but the error class may differ. The differential harness accepts a different class only when Postgres, given the rows stored in key order and with its other indexes set aside, reports the same class as maragudb. Postgres then scans the table or its primary key, which is one of the plans it can pick, and maragudb fails for certain only on a row that every plan reads.

A `SELECT` on several tables evaluates its output and `ORDER BY` on every row of the join, in an order that depends on the plan of the joins, and maragudb cannot rerun it in Postgres's order. So when rows fail with different classes of error, maragudb rejects the statement with `ErrUnsupported`, and when every row that fails fails with the same class, it reports that error, as Postgres does in every order.

A grouped `SELECT` evaluates its `GROUP BY` expressions and the arguments of its aggregates on every input row, and `HAVING`, the output, and `ORDER BY` on every group. Hashed grouping reads every row before it finishes a group, and sorted grouping evaluates the `GROUP BY` expressions of every row before any aggregate and then finishes each group in turn, so the order of the errors depends on the plan. maragudb reports an error when every row and group that fails fails with the same class, as Postgres does in every order, and otherwise rejects the statement with `ErrUnsupported`. A group whose row fails is not finished, so its `HAVING` and output are not evaluated.

An INSERT checks its rows in the order it lists them, as Postgres does, and so reports the same row's error. The rows that foreign key actions change are visited in key order too, and the rerun of the differential harness stores every table in key order. When the actions and checks of several foreign keys fail for one row, maragudb reports the first in the order the foreign keys were created, which is Postgres's order while the object identifiers of their triggers have the same number of digits.

## Remaining differences

For the statements it accepts, maragudb has one known difference from Postgres. It has a `DEV-` ID and its own test in `/internal/pgdiff/unsupported_test.go`, which runs the example on both databases.

- **A condition that can fail on a row that the primary key does not select.** `DEV-20` maragudb evaluates the conditions of a `WHERE` clause only on the rows that its primary key conditions select, as Postgres does when it scans the primary key index. Postgres in its default configuration can scan the whole table instead, for example when the table is small, and then it evaluates the conditions on every row. When a condition fails on a row that the key does not select, Postgres fails and maragudb does not. On a table `acct` with the rows `(1, 100)`, `(2, 50)`, and `(9, -9223372036854775808)`, after `ANALYZE`, Postgres fails `UPDATE acct SET b = b - 10 WHERE id IN (1, 2, 3, 4, 5) AND b - 10 >= 0` with bigint out of range on the row 9, and maragudb updates the rows 1 and 2. With `enable_seqscan = off`, Postgres updates the rows 1 and 2 too. The differential harnesses run Postgres with that setting. So here maragudb is more lenient than Postgres.
