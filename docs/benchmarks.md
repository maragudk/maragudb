# Benchmarks

maragudb's cost is in its requests to the object store: how many of each kind an operation makes, how many bytes they move, and how long each round trip takes. The benchmark suite in `internal/bench` measures these for eight workloads in the style of YCSB, scaled for a small application database. It has two parts:

- **The gate.** `make test` runs every workload in virtual time over the fake store, and fails when a number gets worse than the committed baseline.
- **The measurement.** `make bench` runs the same workloads in real time against Tigris, and writes the latencies, throughput, and cost into this document. It never runs in CI.

## The dataset

`bench.Load` creates one table, `usertable (id bigint PRIMARY KEY, name text, score bigint, payload text)`, with 100,000 rows of about 130 bytes each. It inserts them in batches of 5,000 rows, with maintenance after each batch, as background maintenance would run. Before each workload, maintenance runs until no compaction is due, so that every workload starts from a maintained database.

The workloads choose rows by a Zipf distribution with a skew of 1.1, and scatter its ranks over the ids, as YCSB does, so that the hot rows are not neighbors. YCSB's skew is 0.99, but Go's generator needs a skew above 1. The read workloads have a memory cache of 4 MiB, about a quarter of the database, so that some reads miss it. The others have the default of 64 MiB. Each client is a process of its own: its own driver, engine, and caches.

## The gate

The gate runs each workload over a copy of the loaded database in the simulator's scheduler. Every request takes a fixed virtual latency, from 15 ms for a conditional GET to 50 ms for a conditional PUT, and the clients take turns at each request. The run is the same every time, also with several clients, so the gate can compare exact numbers. The latencies only decide how the clients interleave, and so how often their commits conflict; the gate does not check them.

For each workload, the gate measures per operation:

- GETs, conditional GETs, PUTs, conditional PUTs, DELETEs, and LISTs;
- bytes read, bytes written, and of those the bytes of the manifest;
- conflicts, which are manifest writes that failed their precondition, and retries, which are transactions that the client ran again;
- the hit rates of the memory and the disk cache;
- the bytes that compaction wrote per committed byte, and the segments at the end.

The baseline is in `internal/bench/testdata/baseline.json`. A higher count, or a lower hit rate, fails `make test` with the workload, the metric, and the old and new values. So does a metric that appears or disappears: a count of zero is left out, and the gate cannot tell a count that fell to zero from one that is no longer measured. A better number passes, and the test log and the verification report show it. `make bench-ratchet` rewrites the baseline, for an improvement or for a cost that a change accepts on purpose. With the race detector, the package takes about 10 seconds on its own, and about 35 seconds when it runs next to every other package on 10 cores, against 80 seconds for the simulator.

## The measurement

`make bench` uses the credentials of the Tigris suite, from the environment or from `.env`. It loads the dataset under a prefix of its own, runs the workloads one after another on that one database, and deletes the prefix at the end. Workloads with several clients run them as goroutines. The cost per million operations comes from the requests that the run counted, at Tigris's prices for Standard storage in a global or single region, read from <https://www.tigrisdata.com/pricing/> on 2026-11-07:

- Class A requests, such as PutObject and ListObjectsV2: $0.005 per 1,000.
- Class B requests, such as GetObject and HeadObject: $0.0005 per 1,000.
- DELETE requests and data transfer out: free.
- Storage: $0.02 per GB and month, where Tigris's GB is 2^30 bytes.

The cost leaves out the free allowance of each month.
