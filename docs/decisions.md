# Project Decisions

This document records significant architectural and design decisions made throughout the project's development.

## 2026-11-03: Embedded SQL database with S3 as the only durable state

maragudb is an embedded Go library, like SQLite. All durable state lives in S3-compatible object storage. Caches in memory and on local disk are allowed in the style of turbopuffer, but correctness never depends on them. The target workload is small OLTP app databases.

Alternatives considered:
- A standalone server with a wire protocol. Rejected for now because it adds operational parts and makes testing harder.
- SQLite plus Litestream or LiteFS. This already exists and keeps a local disk as the source of truth, so it is not what this project is for.

## 2026-11-03: Multi-writer optimistic concurrency, strict serializable

Any number of processes can read and write the same database. A commit is a compare-and-swap write that uses S3 conditional writes (`If-Match` / `If-None-Match`), so no external lock service is needed. The isolation level is strict serializable, because it is the easiest guarantee to state and to verify with a history checker.

At first, conflicts are detected at database granularity: any concurrent write commit is a conflict. Single statements outside a transaction retry automatically. Explicit transactions get a typed retryable error. This costs throughput under contention, which is acceptable for small OLTP workloads, and finer granularity can come later.

Alternatives considered:
- Single writer with a lease. This is simpler, but it is close to what Litestream and LiteFS already do.
- Snapshot isolation. It allows more concurrency, but it permits write skew and is harder to test.

## 2026-11-03: Own SQL flavor with Postgres semantics and Go-like types

The SQL dialect is our own. It follows Postgres semantics where they are sensible, and it has none of SQLite's quirks: no type affinity and no implicit coercion. The types map to Go:

- `int` (int64, overflow is an error)
- `float`
- `bool`
- `string`
- `bytes`
- `time` (a UTC instant with nanosecond precision)

Features are added in sections, so the project does not try to reproduce all of Postgres.

Postgres is the differential test oracle. Generated query ASTs are rendered to both dialects, and the results are compared. Intentional deviations are documented and tested.

## 2026-11-03: `database/sql` driver with explicit registration

The API is a `database/sql` driver. It is registered with `maragudb.RegisterDriver(maragudb.Options{...})` instead of an `init` side effect, following the pattern in maragudk/sqlite. This keeps compatibility with sqlc and existing code, and the defaults are opinionated and explicit.

## 2026-11-03: Automated verification only, with in-house deterministic simulation testing

The code is not reviewed manually, so automated tests are the quality gate. Correctness is verified by:

- A seeded deterministic simulator. Concurrent clients run against a fault-injecting fake S3, and the faults include errors, latency, lost acknowledgements, and crashes.
- History checkers for strict serializability.
- Mutation checks that prove the checkers can fail.
- Hegel property-based tests.
- Differential testing against Postgres.
- An integration suite against Tigris.

The design is Antithesis-ready, with SDK assertions and a docker-compose harness, but the project does not depend on the Antithesis platform. This is because the platform is commercial and its instrumentation targets amd64 only.

## 2026-11-03: Storage layout: a CAS-replaced manifest over immutable B+tree segments

Context: the core must give strict serializable multi-writer commits with nothing but S3 conditional writes, O(1) PUTs per commit, and O(log n) GETs per cold point lookup.

Decision: one JSON manifest object at `<prefix>/manifest` is the root of the database. It lists the live segments, a garbage list, and a window of the last 128 commit records. Every commit writes one immutable segment object (a sorted run laid out as a B+tree of blocks, read with range GETs) and then replaces the manifest with `If-Match: <etag>`. Conflict detection is the manifest ETag, so it is at database granularity, as the requirements allow for section 1. Compaction merges every segment into one and moves the old ones to the garbage list. A commit whose answer is lost is resolved by reading the manifest back: the commit landed when the record at its sequence number carries its commit ID, it lost when another ID is there, and it is retried with the same body and ID while the manifest is unchanged, so a commit can never be applied twice. Only when the store stops answering altogether does the client get `ErrCommitUnknown`.

Alternatives considered:
- An append-only log of commit objects with the manifest as a pointer. Rejected because a reader would have to replay the log, and the number of objects would grow with commit count until compaction.
- A per-key or per-range conflict check. Deferred, as the requirements say; the manifest layout leaves room for it later because segments carry key ranges.

## 2026-11-03: Garbage collection by stamped grace period and sequence-number fencing

Context: GC must never delete an object that a reader within the grace period can still reach, and it must be able to clean up objects left by crashed commits, without any coordination between processes.

Decision: segment keys embed the manifest sequence number they were written against (`seg/<seq>-<id>`). An object that is in neither the segment list nor the garbage list is an orphan, and it is deleted as soon as the manifest sequence has moved past its base sequence, because the conditional write that would have referenced it can no longer succeed. Objects that leave the segment list enter the garbage list unstamped; the first GC pass that sees them stamps them with its own clock, taken after it read the manifest, and a later pass deletes them once the stamp is older than the grace period. Readers sample their start time before their freshness read, so a reader younger than the grace period always precedes the stamp and never loses an object. A reader older than the grace period gets `ErrSnapshotExpired`.

Alternative considered: stamping at compaction time. Rejected because the compactor samples its clock before its conditional write lands, which lets a reader that began in between lose objects slightly before its grace period ends.

## 2026-11-03: Deterministic simulation with a cooperative scheduler in virtual time

Context: the simulator must reproduce a history exactly from its seed, but Go schedules goroutines nondeterministically.

Decision: simulated processes run as goroutines under `sched.Scheduler`, which hands a single baton to one task at a time. The only yield points are the fake store's requests, which sleep for a seeded virtual latency, and explicit pauses. Fault decisions, latencies, commit identifiers, and the engine's clock all derive from the seed, and the engine starts no goroutines of its own. The same seed therefore produces an identical history, and a failure is replayed from the seed alone.

Alternative considered: `testing/synctest` with a fake clock. Rejected because the order in which goroutines wake at the same instant is still up to the Go scheduler, so histories would not be byte-identical across runs.

## 2026-11-03: SQL layer: hand-written parser, rows keyed by primary key, statement-level atomicity, strict typing

Context: section 1 needs a SQL surface over the key-value core, and the project's own dialect follows Postgres semantics without SQLite's quirks.

Decisions:
- The lexer, parser, binder, and executor are written by hand in `/internal/sql`. A parser dependency would bring a dialect that is not ours and far more syntax than the sections need, and a hand-written recursive-descent parser with the Postgres precedence table is small.
- Every table has a primary key and there is no hidden row id. A row lives at `r/<table>\x00<key>`, where the key is the order-preserving encoding of the primary key columns, and the table definition at `c/<table>`. Point lookups and range scans on the primary key fall out of the key encoding, and the catalog is transactional because it is just more keys.
- Statements are atomic on their own: a statement buffers its writes and applies them to the transaction only when it succeeds, so a failed statement leaves the transaction usable. Postgres aborts the whole transaction instead; this is recorded as an intentional deviation.
- Types are strict: there is no implicit coercion, a parameter of the wrong Go type is an error, and the only adaptation is the one Postgres applies to literals, an integer literal next to a float. Everything else that Postgres coerces implicitly is a type error here, documented in `/docs/deviations.md`.

Alternatives considered: a hidden row id, as SQLite has, which would make primary keys optional but puts every lookup through a secondary structure; and Postgres's transaction abort on error, which is safer for scripts but makes `database/sql` callers handle an aborted state they rarely expect.

## 2026-11-03: Postgres is the oracle through a shared AST, with Postgres 18 in Docker and `COLLATE "C"`

Context: acceptance criterion 4 asks for differential testing against Postgres, and the two dialects differ in syntax and type names.

Decision: hegel generates a schema, rows, and statements as the `ast` package's syntax tree, which renders to both dialects; the harness in `/internal/pgdiff` runs each statement on both and compares results, exactly when `ORDER BY` determines the order and as multisets otherwise. Postgres 18 runs in a Docker container locally and as the shared workflow's service in CI, with a database created from `template0` with the `C` locale so that strings compare by byte order on both sides. The harness fails rather than skips when neither is available. `pgx` is the test dependency for the Postgres side. Every intentional difference is listed in `/docs/deviations.md` with its own test that asserts the difference on both databases, so the list cannot drift from the behavior.

Alternative considered: comparing against SQLite, which the requirements interview rejected because the dialect must not inherit SQLite's quirks.

## 2026-11-03: Automatic maintenance coordinated by an S3 lease that only saves work

The driver runs compaction and GC in the background. Maintenance is on by default and can be turned off. Clients coordinate through a lease object in S3, with a timeout. A client acquires the lease with `If-None-Match: *` and renews it or takes it over with `If-Match`.

The lease is only an efficiency optimization, and correctness never depends on it. Compaction is a conditional commit like any other, and GC needs no coordination, because a delete can safely happen twice. If two clients both believe they hold the lease, they duplicate work and nothing else. This is why the lease needs no fencing tokens and no assumption about clock sync. The simulator must show that correctness holds with the lease disabled and with leases that overlap.

Compaction also rebases on a conflict. When the commits that won against it only added segments, it reapplies its swap on top of them instead of redoing the merge. This means steady write traffic no longer starves compaction, which is a problem the lease cannot solve.

Alternatives considered:
- Manual `Compact` and `GC` only. This is easy to forget, and the database slowly degrades.
- Every client maintaining on its own, with no lease. This is safe but wastes requests and work when there are many clients.
- A lease that correctness depends on. This would need fencing, and it would make clock skew a safety issue.

## 2026-11-04: Custom object stores through an unexported interface on `Options.Store`

`Options.Store` accepts any value with four methods, `Get`, `Put`, `Delete`, and `List`, whose signatures use only exported types from the `maragudb` package (`GetOptions`, `PutOptions`) and builtin types. The interface itself is unexported, following the pattern of private interfaces on the consuming side. The exported sentinel errors `ErrObjectNotFound`, `ErrPreconditionFailed`, and `ErrNotModified` are part of the contract. An adapter inside the package translates to the engine's internal client and refuses answers that would silently break correctness, such as an empty ETag.

Alternatives considered:
- Exporting the internal client interface and its types. This would make the internal storage contract public and hard to change.
- An exported interface type. It adds surface without letting callers do anything more.

## 2026-11-04: The Antithesis harness runs against a real S3-compatible store and the in-process simulator

The docker-compose harness in `/antithesis` has two containers: versitygw as the S3-compatible store, and an instrumented workload. Test commands run the bank and list-append workloads through the engine and through SQL against versitygw over the network, so that Antithesis's own faults (partitions, resets, pauses, killed containers) reach the real AWS client and the commit protocol. Another test command runs the deterministic simulator against the in-process fake, with seeds from the Antithesis SDK, to cover crash points that the network cannot inject on demand.

Alternatives considered:
- The in-process fake only. Antithesis's network faults would not reach a store in the same process, so the run would only explore simulator seeds.
- MinIO. Its images are no longer published on Docker Hub.

## 2026-11-04: Orphans are stamped like other garbage, because compaction rebases

Context: the garbage collection decision of 2026-11-03 deleted an object that no manifest referenced as soon as the manifest sequence had moved past the object's base sequence, because the conditional write that would have referenced it could no longer succeed. The compaction rebase in the automatic maintenance decision breaks that reasoning: when its manifest write loses to commits that only added segments, compaction reapplies its swap on top of the newer manifest, so its output can still enter the manifest after the sequence has moved past its base.

Decision: an unreferenced object is no longer deleted at once. The first GC pass that sees it adds it to the garbage list with a stamp, and a later pass deletes it after the grace period, exactly like an object that left the segment list. A compaction gives up instead of rebasing once it is older than half the grace period, and a rebased manifest drops the stamp on its own output. The stamp is taken after the pass read a manifest newer than the one the compaction read, so it is later than the compaction's start, and the deletion comes a whole grace period after the stamp, so the compaction's last conditional write has at least half a grace period to land. Readers get the full grace period, because a reader that loses an object only fails one transaction, while a manifest that references a deleted object would be permanent. GC reapplies its pass on top of commits that landed meanwhile for the same reason compaction does: under steady writers a pass whose write always lost would delete the same expired objects on every run and never shrink the garbage list. Only the garbage it found unstamped gets its stamp; garbage that entered the list after the pass began waits for the next pass.

Alternatives considered:
- Writing the compacted segment again under the new base sequence on every rebase. This keeps the old orphan rule but costs a write of the whole database per rebase, several times under steady writers.
- Deleting orphans at once unless they come from a compaction, told apart by their key. This keeps crashed commits' orphans short-lived but adds a second rule for the same question; one rule is easier to show correct.

## 2026-11-04: A strict subset of Postgres instead of our own SQL flavor

This replaces "Own SQL flavor with Postgres semantics and Go-like types" from 2026-11-03.

maragudb accepts a subset of Postgres SQL, and the same SQL text runs on both systems. For every statement that maragudb accepts, the result must be identical to Postgres. When Postgres fails a statement, maragudb fails it too, and with the same error class wherever the error does not depend on evaluation order. The planner may differ, because only results are compared.

maragudb may be stricter than Postgres. It can reject statements that Postgres accepts, such as those that depend on implicit casts, as long as it rejects them with a clear error. A stricter rejection never changes what an accepted statement returns. Unsupported features are listed as unsupported. They are not semantic deviations.

Consequences:
- Type names are Postgres names: `bigint`, `double precision`, `boolean`, `text`, `bytea`, `timestamptz`. The Go-like names are dropped.
- `timestamptz` has microsecond precision, as in Postgres.
- The rest of the behavior must also match Postgres exactly. For example, a failed statement aborts the transaction until rollback, and `lower` and `upper` follow the C locale.
- The differential harness runs one SQL string on both sides, so there is no second renderer.
- External Postgres-syntax test corpora become usable as additional oracles.
- sqlc's PostgreSQL engine and existing Postgres knowledge carry over.

Some Postgres features will deliberately never be supported, because they are common antipatterns. The `money` type is one example. That list is decided later.

Alternatives considered:
- Keep our own flavor with documented deviations. Rejected because every deviation is something a reader must trust separately, and because the second renderer is extra code that itself needs verification.
- Postgres semantics with Go-like aliases for the type names. Rejected because it breaks the guarantee that the same text runs on both systems.

## 2026-11-04: A machine-checked map from requirements to tests, and a report for every run

The code is never reviewed, so trust rests on whether the verification is complete. The goal of this mechanism is that a reader can judge that completeness from the docs and the CI output alone.

Every claim gets a stable ID:
- `AC-` for acceptance criteria
- `INV-` for key invariants
- `DEV-` for documented differences from Postgres
- `MUT-` for deliberate bugs
- `STATE-` for hard states that the simulator must reach, such as a lost acknowledgement or a lease takeover

A test declares which IDs it verifies with `verify.Covers`, using string literals only, so that the declarations can be parsed statically. A meta-test fails when any of these hold:
- an ID has no verifying test
- a test names an unknown ID
- a deliberate bug is detected by nothing
- a declared state goes unreached in the fixed corpus
- the generated `docs/verification.md`, together with its table of which checkers catch which bug, is out of date

Each test run records facts such as runs, anomalies, deliberate bugs caught, differential statements, request budgets, and latencies. The run renders them as a report: `make report` locally, and in the GitHub Actions job summary in CI.

Every future change must keep this map complete. New requirements, deviations, deliberate bugs, and hard states get IDs and verifying tests in the same change.

Alternative considered: a hand-maintained list of what is tested. Rejected because nothing would catch it going stale, and without that check the list would not be a trust signal.

## 2026-11-04: Reject outcomes that depend on Postgres's plan, instead of emulating its planner

Context: under the strict-subset decision, every accepted statement must give the same result as Postgres. Some Postgres outcomes depend on its planner or on the physical order of rows: the order in which it evaluates WHERE conditions, whether an index scan skips rows that would fail, which rows a LIMIT reads, the order in which an UPDATE checks moved keys, and whether it evaluates a stable expression while planning.

Decision: maragudb does not reproduce Postgres's cost model or plan choice. It rejects such a statement with `ErrUnsupported`, statically where the shape decides it, such as a condition that can fail next to a primary key condition or under a LIMIT, and at run time where the data decides it, such as a condition that fails on a row that another condition rejects. A statement that fails in every order still fails with its own error. Parameters take their type from their context as in Postgres, and a Go value that drivers would convert in different ways is rejected too.

Alternatives considered:
- Emulating the planner's conjunct order by estimated cost and equivalence classes, as the first draft did. Rejected because it depends on cost constants and plan choices that change between Postgres versions and table statistics, so the emulation could silently diverge.
- Evaluating every row in a full scan to decide plan dependence exactly. Rejected because it would turn point lookups into full scans whenever a condition can fail.

## 2026-11-04: A primary-key condition fixes the plan to an index scan

Context: the previous decision rejects a condition that can fail when it sits next to a primary-key condition. That rejects natural OLTP statements such as `UPDATE acct SET b = b - $1 WHERE id = $2 AND b - $1 >= 0`. With an index scan, Postgres evaluates `b - $1` only on the row that the key selects. With a sequential scan, it can raise an overflow error on another row.

Decision: maragudb accepts these statements and behaves as Postgres does with the primary-key index. It evaluates the other conditions only on the rows that the key condition selects. The rules for WHERE order and LIMIT stay as they are. The differential harness runs Postgres with `enable_seqscan = off`, so Postgres uses the same plan and the comparison stays deterministic. Postgres in its default configuration can choose a sequential scan, for example on a small table, and then fail on a row that the key does not select. In that case maragudb is more lenient than Postgres. This is a documented `DEV-` difference with its own test.

Alternatives considered:
- Keep rejecting. Rejected because it refuses the statements that small OLTP apps write most.
- Evaluate the conditions on every row, as a sequential scan does. Rejected because every point update would cost O(table).

Also decided: `integer` stays a type for literals only. It is not a column type for now, so the column types stay a small set to test.

Markus left both choices to the lead.

## 2026-11-06: With several indexes, a row is skipped only when every scan Postgres could pick skips it

Context: the previous decision fixes the plan to a scan of the primary key index, because with `enable_seqscan = off` Postgres always scans it when a condition can use it. With secondary indexes, Postgres chooses by cost between the primary key, the other indexes, and bitmap combinations of them. Each scan has its own index conditions, so the rows on which Postgres evaluates the other conditions depend on the plan again. EXPLAIN on Postgres 18 shows that it can also scan a whole index without index conditions, when `ORDER BY` sorts by the index's first column or when the index has every column a query reads.

Decision: maragudb models the plans instead of choosing one. A condition that cannot fail and compares a column with a constant, an `IN` of constants, or a boolean column is an index condition of every scan of every index on that column, as EXPLAIN shows. An index is a candidate scan when it has such a condition, or when Postgres could scan it without one: another condition could use it, also inside an `OR`, `ORDER BY` sorts by its first column, or it covers every column of a `SELECT`. When a condition can fail, maragudb skips a row only when every candidate rejects it by one of its index conditions, and when some candidate has no index condition, it skips no row. On every other row, the runtime check of `UNS-ORDER-DEPENDENT-WHERE` applies as before. So a statement whose outcome differs between candidate plans is rejected at run time, and one whose outcome is the same in all of them gives Postgres's result. maragudb itself reads the union of the candidates' rows in that case, and otherwise the narrowest index. It visits the rows in key order whenever a row can fail, and in index order only when nothing can fail, such as for an `ORDER BY` with `LIMIT` that an index sorts.

The differential harness reruns a statement whose error class differs with the rows stored in key order, as before, and now also with the table's other indexes marked invalid in `pg_index` for the rerun, so that Postgres scans the table or its primary key. An invalid index is still updated and still enforces uniqueness.

Alternatives considered:
- Emulating Postgres's cost model to pick the same index. Rejected for the same reasons as in the decision of 2026-11-04: it depends on statistics and cost constants.
- Treating only the conditions common to every index as index conditions. Rejected because a row that one index's conditions reject can still be read by another index, so it is not sound.
- Rejecting every condition that can fail on a table with secondary indexes. Rejected because it refuses the point updates that the previous decision exists for.

## 2026-11-06: Foreign keys fire in Postgres's trigger order, and a DELETE whose actions could depend on that order is rejected

Context: Postgres implements foreign keys with triggers. At the end of each statement it fires, for each row in the order it visited them, the actions and checks of every foreign key that references the row's table, in the order of the triggers' names, and then the checks of the row's own foreign keys. An action such as `ON DELETE CASCADE` is a statement of its own, whose triggers fire when it ends. The trigger names contain object identifiers, so their order follows the creation order of the foreign keys only while the identifiers have the same number of digits. Experiments on Postgres 18 show that the outcome can depend on that order: with a child that references a parent by one column with `NO ACTION` and by another with `ON DELETE CASCADE`, deleting a parent that one child references by both fails or succeeds depending on which foreign key was created first, and with several parents it depends on the order of the rows too.

Decision: maragudb fires the same events in the same order: rows in key order, the referencing foreign keys in the order they were created, and the row's own foreign keys after them. An action's own events join the end of the statement's queue, because Postgres runs an action's query without firing its triggers when it ends (`ri_PerformCheck` passes `fire_triggers = false`), so they fire after every event queued before them. maragudb works the queue as a list, without recursion, so a cascade down a chain of any length does not grow the stack, and Postgres handles a chain of 100,000 rows too. It follows Postgres's details: NO ACTION first looks for another row with the old key, RESTRICT does not, SET DEFAULT checks the old key again as NO ACTION does, right after its update, a check is skipped for a row that a later write of the statement changed, and the check of an updated row runs also for unchanged keys when the transaction wrote the row before. Where the order could change the outcome, maragudb rejects the statement with `UNS-FOREIGN-KEY-ORDER`: a DELETE whose actions could write columns that a check of the same DELETE reads, or that could write one table through two foreign keys other than by deleting rows. Under those conditions every order gives the same outcome, and only the class of the error can differ between orders when several things fail, which is an error that depends on order, as for the rows of a statement. maragudb supports only `NO ACTION` and `RESTRICT` for `ON UPDATE`, only `MATCH SIMPLE`, and no foreign key on double precision columns, so that keys never change through an action and equal keys are equal by their encoding. The differential harness stores every table in key order, with the triggers off, for its rerun.

Also decided: `now()`, `transaction_timestamp()`, and `CURRENT_TIMESTAMP` are the start of the transaction on the engine's clock, which is the virtual clock in the simulator, and the other clocks are unsupported. A `DEFAULT` or `CHECK` whose constant part fails is rejected when the table is created, because Postgres folds it only when a statement uses it and fails then in an order maragudb does not reproduce. Constraint names share one namespace across tables, recorded at `k/<name>\x00<table>`, because Postgres chooses the names of new constraints, and of the indexes of `PRIMARY KEY` and `UNIQUE`, to differ from every constraint in the schema.

Alternatives considered:
- Final-state semantics: apply every action first and check every constraint at the end. Rejected because Postgres's checks see intermediate states, so the outcomes differ exactly in the cases where the order matters.
- Rejecting every foreign key action. Rejected because cascades and `SET NULL` through chains of tables and self-referencing trees are what applications need, and they are order-independent.
- `ON UPDATE CASCADE`, `SET NULL`, and `SET DEFAULT`. Deferred: a cascaded key update moves keys in other tables, with the order questions of `UNS-KEY-UPDATE-ORDER` in every table it reaches.

## 2026-11-06: A join is accepted only when no condition that can fail fails on any row or combination of rows that a plan could evaluate it on

Context: Postgres chooses the order of the joins of a query and the method of each, a nested loop, a hash join, or a merge join, by cost, and turning off sequential scans does not fix the choice. EXPLAIN on Postgres 18 shows that it pushes a condition on one table into the scan of that table, also on the right side of a LEFT JOIN, that a strict WHERE condition on that side turns the join into an inner join, and that equalities derive conditions on other tables. Which rows and pairs of rows a condition is evaluated on then depends on the plan: a hash join evaluates the other conditions of a join only on the pairs with equal keys, a nested loop with an index scan only on the rows the index finds, a merge join stops at the end of either side, and a join with an empty side may never scan the other side. The same statement fails with one method and succeeds with another, also when the condition fails on every row of one table, and `enable_nestloop`, `enable_hashjoin`, and `enable_mergejoin` each change the outcome.

Decision: maragudb keeps the rule of the single-table decisions, that it accepts a statement only when every plan Postgres could choose gives the same outcome, and checks it at run time. Before a join runs, it evaluates every condition of WHERE and ON that can fail on every row and combination of rows that a plan could evaluate it on: the rows that some scan of each table could read, by the candidate scans of the several-indexes decision, where an index on any column that a condition or ORDER BY reads is a scan Postgres could pick, with a row of NULLs for a table on the right side of a LEFT JOIN, and also each side of a comparison alone, which is the key of a hash join or a merge join or the value of an index scan, and the condition that Postgres takes out of an OR for the scan of one table. It rejects the statement with `UNS-PLAN-DEPENDENT-JOIN` when one of them fails, or when they are more than 100,000. When none fails, no plan fails, and the join gives the same rows in every plan, so maragudb runs it in any order: nested loops with index lookups on equalities, in an order that follows the conditions. The output and ORDER BY are evaluated on every row of the join in every plan, so a failure there fails in every plan; maragudb reports it when every row that fails fails with the same class, and rejects the statement otherwise, because which row Postgres reaches first depends on its plan. A LIMIT on a join needs an ORDER BY on every primary key column of every table, and nothing that can fail.

The harnesses keep only `enable_seqscan = off`. Turning off join methods would not make the comparison deterministic, because the rule does not depend on which method Postgres picks, and a harness that compared against one method could hide a statement that fails with another.

Alternatives considered:
- Rejecting every condition that can fail in a query on several tables. Rejected because it refuses the joins whose conditions add or multiply columns, which are common and almost never fail, as the sqllogictest corpus shows.
- Treating a condition that fails on a row that every plan reads as a certain failure, as the single-table rule does. Rejected because no row is read by every plan of a join: a join with an empty side may never scan the other one.
- Emulating Postgres's choice of join order and method. Rejected for the reasons of the decision of 2026-11-04: it depends on statistics and cost constants.

## 2026-11-06: numeric exists only as the result type of SUM and AVG over integers

Context: in Postgres, `SUM(bigint)`, `AVG(bigint)`, and `AVG(integer)` return numeric, and `SUM(integer)` returns bigint. maragudb had no numeric type. Rejecting these aggregates would refuse the most common aggregates of an app, such as a total of amounts. Markus made the call.

Decision: a value of type numeric exists only as the result of these aggregates. It is exact: `SUM` adds in arbitrary precision, and `AVG` divides the sum by the count as Postgres's numeric division does, rounded half away from zero to the scale that Postgres's `select_div_scale` picks, at least 16 significant digits, with trailing zeros, so `AVG` of 1 and 1 is `1.00000000000000000000` and `AVG` of 1, 2, and 2 is `1.6666666666666667`. The value is kept as Postgres's text, which reaches Go through `database/sql` as a string, and `ColumnTypeDatabaseTypeName` reports `NUMERIC`, as Postgres drivers do. It supports comparisons with another numeric, with integers and bigints, which are converted to numeric, and with double precision, to which the numeric is converted through its text, and `ORDER BY`, `DISTINCT`, `IS NULL`, `CASE`, `COALESCE`, `NULLIF`, `||`, and casts to bigint, rounded half away from zero and with Postgres's out of range error, to double precision, and to text. maragudb rejects arithmetic on numeric, a numeric literal next to it, and a quoted literal that Postgres reads as numeric with `ErrUnsupported` under `UNS-NUMERIC`. Numeric columns and casts to numeric stay rejected under `UNS-TYPES`, and `NUMERIC` columns stay out of scope.

Also decided: a `SUM` or `AVG` of double precision is accepted only when its result cannot depend on the order of addition, which maragudb checks at run time (`UNS-FLOAT-SUM`). Grouped queries follow the plan rules of `WHERE` and of joins: the conjuncts of `HAVING` without aggregates move into `WHERE`, as in Postgres; a `LIMIT` on groups needs an `ORDER BY` on every `GROUP BY` expression and nothing that can fail; `MIN` and `MAX` that Postgres can compute from an index reject a `WHERE` condition that fails; and errors in the arguments of aggregates, in `GROUP BY`, in `HAVING`, and in the output are reported only when every failure has the same class. The rules were proven with `EXPLAIN` on Postgres 18 and are pinned in `TestAggregatePlans` in `/internal/pgdiff/aggregates_test.go`.

Alternatives considered:
- Rejecting `SUM` and `AVG` of bigint and integer. Rejected because it refuses the most common reporting queries of an OLTP app, such as a total of amounts.
- A full numeric type, with columns, literals, and arithmetic. Rejected for now because Postgres's numeric arithmetic has its own scale rules for every operator, NaN and infinities, and a large input syntax, each a surface to verify. The result type alone needs only the scale of division.
- Approximate comparison: returning `SUM` and `AVG` as double precision, or comparing them approximately. Rejected because the results would differ from Postgres's in their text and in their last digits, and the strict subset allows no such difference.

## 2026-11-06: Arithmetic on numeric results follows Postgres's scale rules, and numeric literals and functions stay unsupported

Context: the decision above made numeric the result type of `SUM` of bigint and `AVG` of integers, and rejected arithmetic on it. That rejection was the largest aggregate-related one in the SQLite sqllogictest corpus, 54,509 statements, and it refuses common report queries such as `SUM(a) - SUM(b)` and `-SUM(x)`. The arithmetic is cheap to add: each result is exact or rounded deterministically from its operands, so every plan gives the same value, and division with Postgres's scale rules was already ported for `AVG`.

Decision: unary `-` and `+`, and binary `+`, `-`, `*`, `/`, and `%` are supported where at least one operand is such a numeric, a result of `SUM` or `AVG` or of arithmetic on one, and the other is numeric, integer, or bigint. Integers and bigints convert to numeric, as Postgres's implicit casts do, and the result is numeric. The scales are Postgres's: `+` and `-` are exact with the larger scale of the operands; `*` is exact with the sum of the scales, rounded half away from zero to 16383 digits after the point when the sum is larger; `/` rounds half away from zero to the scale that `select_div_scale` picks, enough for at least 16 significant digits, judged from the first base-10000 digits of the operands, at least the scale of either operand, and at most 1000; `%` is `a - trunc(a / b) * b`, exact, with the sign of `a` and the larger scale. Unary minus keeps the scale, and the negation of zero is zero without a sign, so `-(0.00)` is `0.00`. Thus `1.5 * 2.25` is `3.375`, `-7.5 / 2` is `-3.7500000000000000`, `7.50 % 2` is `1.50`, and `1 / 3.0` is `0.33333333333333333333`. Division and `%` by zero fail with SQLSTATE 22012, and a result with more than 131072 digits before the point fails with 22003, "value overflows numeric format", as in Postgres.

With a double precision operand, the numeric converts to double precision and the result is double precision, as in Postgres; `%` with a double precision operand does not exist there and fails with 42883. Postgres converts by formatting the numeric as text and reading it with `strtod`, which rounds correctly on its glibc. maragudb converts with Go's `strconv.ParseFloat`, which also rounds the exact decimal to the nearest double, ties to even, so both sides give the same double. The conversion fails with 22003, as Postgres's `float8in` does, when the double would be infinite, or zero for a numeric that is not zero, which a numeric can become after many divisions. A property test checks the conversion against exact rational rounding, also at midpoints between doubles and at subnormals, and pgdiff tests check the out-of-range errors against Postgres. Comparisons with double precision used the same conversion already; the underflow could not happen before arithmetic existed.

The plan rules of the decision above hold: every plan gives the same value, and errors in the output are reported only when every failure has the same class. Unary minus and plus cannot fail, so a `LIMIT` on groups allows them; `+`, `-`, `*`, `/`, and `%` can fail, like integer arithmetic, so `UNS-PLAN-DEPENDENT-LIMIT` rejects them under such a `LIMIT`. Arithmetic makes numerics of different scales in one column more common, such as `AVG(x) * 0` per group, and `UNS-DISTINCT-ZERO` still rejects a `SELECT DISTINCT` with such equal values of different scales.

Still rejected under `UNS-NUMERIC`: numeric literals such as `1.5`, `1e3`, or an integer beyond the bigint range, also next to a numeric result, such as `SUM(x) * 1.5` or `AVG(x) > 1.5`; a quoted literal that Postgres would read as numeric, such as `SUM(x) = '5'` or `AVG(x) * 2 > '5'`; every function of numeric, such as `abs(AVG(x))` or `round`; and aggregates over a numeric argument. Numeric columns and casts to numeric stay rejected under `UNS-TYPES`. The decision above is not edited; this one supersedes what it says about arithmetic.

Alternatives considered:
- Keeping arithmetic on numeric rejected. Rejected because it refuses common report queries such as `SUM(a) - SUM(b)`.
- Supporting numeric literals too. Rejected for now because a literal is numeric in every context, so it would widen numeric to whole expressions, to the neighbours of columns, and to functions, each a surface of its own to verify.
- Rejecting numeric mixed with double precision. Rejected because the conversion was already accepted for comparisons, and both sides round correctly.

## 2026-11-07: A subquery is evaluated completely, everywhere a plan could evaluate it, and a statement whose subquery fails there is rejected

Context: section 3 ends with `IN` and `EXISTS` subqueries, scalar subqueries, subqueries in `FROM`, and non-recursive `WITH`. Postgres plans a subquery in several ways, and EXPLAIN on Postgres 18 with sequential scans off shows that the plan decides whether an expression in or around a subquery is evaluated. An uncorrelated subquery is an InitPlan, which Postgres evaluates lazily when an expression first needs it, before an index scan whose condition it is, also of an empty table, so that `SELECT * FROM e WHERE id = (SELECT x FROM two)` fails with 21000 on an empty `e` while the same comparison on a column without an index succeeds, or never. `IN` and `EXISTS` become semi-joins, `NOT EXISTS` an anti-join, and in Postgres 18 a correlated `IN` too; a semi-join evaluates the conditions of the subquery on its rows as a scan of its own, and the conditions of the query around on rows that the subquery rejects, as a merge join from `a IN (SELECT b FROM u WHERE u.id = 1) AND 10 / w > 0` divides on every row of the outer index. `NOT IN` is a hashed SubPlan. A SubPlan stops at the row that decides it, and a scalar subquery at its second row, so `SELECT (SELECT 10 / w FROM t ORDER BY id)` fails with 21000 on the rows `1, 1, 0` and with 22012 when the zero comes second. `EXISTS` drops the output of its query unless it has aggregates. A subquery in `FROM`, and a CTE read once, are merged into the query around, where an output that nothing reads is never evaluated, while a CTE read twice is evaluated as a whole, and a CTE that nothing reads is neither evaluated nor folded. The rules are pinned in `TestSubqueryPlans` in `/internal/pgdiff/subqueries_test.go`.

Decision: maragudb keeps the rule of the join decision, that it accepts a statement only when every plan Postgres could choose gives the same outcome. It evaluates a subquery by running its query completely, with the plan rules of a statement of its own, whenever the statement around needs its value, and memoizes the result by the row of the query around, or once per statement for an uncorrelated one. When that evaluation fails, the statement is rejected with `UNS-PLAN-DEPENDENT-SUBQUERY`, because a plan that stops earlier, or never evaluates the subquery, may succeed. The only error a subquery reports itself is the 21000 of a scalar subquery with more than one row, which every plan that evaluates it reports. For the statement around, a subquery that can fail is an expression that can fail, so the rules of `WHERE`, of joins, of grouping, and of `LIMIT` decide where it is evaluated: a scalar subquery with two rows fails in the output, where every plan evaluates it, and is rejected in a join condition. On top of that, wherever Postgres can evaluate a subquery without a row of the query around:
- An uncorrelated subquery that can fail in `WHERE`, `ON`, or `HAVING` is evaluated before any row is read, and a failure rejects the statement.
- A correlated `EXISTS` that can fail in a condition is also evaluated with NULL for every column of the query around, which makes its correlated conditions reject every row, so that its conditions that can fail are evaluated on every row its scans could read. A column of the query around counts as a constant for the scans the subquery's conditions could use, and not as an index condition, so those scans read every row a semi-join could.
- A correlated `IN` in a condition whose subquery can fail is rejected, because a semi-join evaluates the subquery's output on rows that no row of the query around matches.
- A subquery in `FROM` and a CTE are evaluated before the statement reads any row, and their conditions take no index conditions when their query can fail. A condition of the query around that reads their columns is rejected when it can fail, or when their query can, since after merging Postgres may evaluate it on rows that the subquery rejects. A `LIMIT` over their rows needs an `ORDER BY` on every column, none of them double precision or numeric.
- A folding error inside a subquery is rejected, because Postgres folds it in an order that merging changes, and never folds an unread CTE.
- A statement that evaluates its subqueries more than 20,000 times is rejected, like a join check beyond 100,000 combinations.

Subqueries read the statement's snapshot, without its own writes, as in Postgres; a write's subquery that reads the table it writes sees the rows as the statement began. With conflicts at database granularity, a commit conflicts with every commit since its snapshot, so the reads of subqueries are in its conflict check as long as they come from that snapshot, also in a retry. The simulator's list-append workload appends to packed lists with a subquery that reads the list, and `MUT-SUBQUERY-STALE-READS`, which keeps the results of an autocommit statement's subqueries across its retries, loses appends that the durability checker finds.

Also decided: a subquery in `FROM` needs an alias, which Postgres 16 made optional; and `ANY`, `SOME`, `ALL`, a row on the left of `IN`, `LATERAL`, `WITH RECURSIVE`, `MATERIALIZED`, a query that writes in `WITH`, `WITH` in front of a write, an aggregate of the columns of a query around, and subqueries in `GROUP BY`, `LIMIT`, `OFFSET`, and the list of an `IN` stay rejected under `UNS-SUBQUERIES`.

Alternatives considered:
- Following Postgres's choice between a SubPlan, a hashed SubPlan, a semi-join, and an InitPlan, and its order of evaluation. Rejected for the reasons of the decision of 2026-11-04: the choice depends on costs and statistics.
- Rejecting every subquery that can fail. Rejected because a scalar subquery of a column can always return two rows, and such subqueries are the common case in the sqllogictest corpus; with the runtime check, all of select1 to select5 runs.
- Evaluating a correlated subquery as a join of its tables with the query around, as the join check does. Rejected for now as a large change; evaluating it on every row the query around reads, plus the NULL run for `EXISTS`, covers the semi-join plans for the subqueries that are accepted.

## 2026-11-07: Stamped garbage lives in chains of immutable garbage batches, which the manifest only references

Context: the manifest listed every object that left the segment list until GC deleted it, a whole grace period later. Every commit rewrites the whole manifest, so on a busy database each commit encoded and uploaded a manifest that grew with the number of commits in the last hour: `index/delete` in the sqllogictest subset made 6,500 commits, which took 101 s, and 10,000 commits 300 ms apart grow the manifest from 27 KB to 1.1 MB. The orphans of failed commits, one per conflict, joined the same list. `AC-6.4` now asks for a manifest whose size does not depend on the number of commits within the grace period.

Decision: the manifest, now version 2, keeps only the keys of the garbage that compaction moved out of the segment list and that no GC pass has stamped yet, plus references to chains of garbage batches. A GC pass writes the keys it stamps, the unstamped garbage of the manifest it read and the orphans it found, into one immutable garbage batch object at `<prefix>/gc/<seq>-<id>`, and the manifest gets a reference to it in the same conditional write that drops those keys from the unstamped list. The batch names the batch before it in its chain. A pass adds its batch to the newest chain while that chain's first batch is less than an eighth of the grace period old, and otherwise starts a new chain. A reference carries the stamp of the chain's first batch, the latest stamp of any of its batches, and the number of objects it keeps. A chain expires once its latest stamp is a grace period old: a pass then deletes its garbage, drops the reference in its manifest write, and only after that write landed deletes the batch objects. So the manifest holds the live segments, the commit records of the last 128 commits, the garbage of the compactions since the last GC pass, and at most about ten chain references, whatever the number of commits; with the default grace period and maintenance, 10,000 commits 300 ms apart write manifests of 12.5 KB after 100 commits and 12.6 KB after 10,000. Each process caches the batches it has read, which are immutable, so a pass reads only the batches that are new to it. A manifest of version 1 fails to open with `ErrUnsupportedManifest`, whose message names both versions; the project is pre-release, so nothing reads the old encoding.

Why GC stays safe:
- A stamp is still the clock of the pass that read the manifest from which the garbage had already left, so every snapshot that still has the garbage began before the stamp. A chain expires on its latest stamp, which is no earlier than the stamp of any garbage in it, so joining a chain only delays a deletion, by at most an eighth of the grace period.
- An orphan can be the output of a compaction or a GC pass that later rebases and lands, and an immutable batch cannot drop its stamp, as the manifest entry used to. Instead, a pass deletes the garbage of an expired chain only when the manifest it read references it in no other way: not as a live segment, not as unstamped garbage, not in a chain that has not expired, and not as a batch object of any chain. Garbage that went back into use and left again is listed again, with a later stamp, and waits for that one. A compaction still gives up once it is half a grace period old, and a GC pass now does too before any manifest write that references a batch it wrote, because another pass may stamp that batch as an orphan once the manifest moved past it and delete it a grace period later.
- The batch objects of a chain are deleted only after a manifest without the chain landed. A pass that read an older manifest and finds a batch gone reads the manifest again, and fails with `ErrConflict` when it moved on. When it did not, the manifest references a missing batch, which must never happen: the pass fails with an error that names the batch, and an Antithesis `Unreachable` assertion marks it, instead of treating the chain as empty.
- The orphan sweep lists `gc/` as well as `seg/`, with the same rule, so a batch whose pass lost, crashed, gave up, or wrote it again for another chain on a rebase, and a batch object whose delete failed after its chain was dropped, is stamped and deleted like any orphan. A reference lost in any other way leaves its garbage unreferenced, and the sweep stamps it again with a later stamp, which is safe.
- A pass reapplies itself on a newer manifest as before. It drops a chain only when that manifest references the same newest batch, so a chain that another pass extended meanwhile stays, and when the chain it was to join changed, it writes its batch again with the new predecessor.

The simulator checks this after every run: a fresh process runs GC a grace period apart until all garbage has expired, and the store must then hold nothing but the live segments and the objects of writes against the final manifest (the storage checker). Some readers now pause for up to the grace period, so that deleting garbage early shows. The mutants `MUT-GC-BATCH-OBJECTS-FIRST`, `MUT-GC-SWEEP-SEGMENTS-ONLY`, `MUT-GC-CHAIN-FIRST-STAMP`, and `MUT-GC-DELETE-REFERENCED` break the new steps, and the kill matrix and engine tests detect each.

Alternatives considered:
- One batch reference per GC pass, without chains. It is simpler, but the manifest then grows with the number of maintenance passes within the grace period, 360 to 720 references per hour at the default interval.
- Rewriting the newest batch with all of its chain's garbage on every pass. Every pass would then write all the garbage of up to an eighth of the grace period, instead of only its own.
- Deriving the garbage from a listing, without recording it. A listing does not tell when an object left the manifest, so the stamps would still need a record.
- Batches for the garbage of compactions only, with orphans listed in the manifest as before. A failed commit leaves one orphan, so the manifest would still grow with the conflicts within the grace period.

## 2026-11-07: Size-tiered compaction of adjacent segments, with a merge of the whole database when the newer segments outweigh the oldest

Context: compaction merged every live segment into one when there were `CompactionThreshold` segments, 8 by default, and every commit adds one. So every 8 commits rewrote the whole database, and the bytes that compaction read and wrote for each committed byte grew with the database size: for the same 1,000 small commits, 523 bytes per committed byte on a database of 2,000 keys and 5,008 on one of 20,000. `AC-6.5` now asks that this grows at most with the logarithm of the size, and the read budgets `AC-5.3`, `AC-5.5`, and `AC-5.8` must still hold, so the number of live segments must stay logarithmic too.

Decision: compaction puts the segments in tiers by their size in bytes, which the manifest already records. Tier 0 holds the segments below 1 KiB, and tier i holds those of 1 KiB·F^(i-1) up to 1 KiB·F^i, where F is the fan-in. `Options.CompactionFanIn` replaces `CompactionThreshold`; it defaults to 4 and is at least 2. A segment counts in the highest tier of itself and every newer segment, so that tiers never rise from the oldest segment to the newest, and a segment that deletes made smaller than a newer one goes with that one. A merge is due when F adjacent segments count in one tier. Each such run is merged in windows from its oldest segment, each of at least F segments and of as many as fit below the limit of the next tier. When there are at least F segments, and those after the oldest one are together at least as large as it, or hold tombstones for at least as many of its entries as remain, the whole database is merged into one segment instead. The tombstones count apart from the bytes because a tombstone is small and can hide a large value, so that a mass delete still frees its space. One compaction merges every due window, writes a segment for each, and swaps them all into the manifest in one conditional write, and a maintenance step compacts again while a merge is due, because one merge can make the next tier due. `maragudb.Compact` still merges everything, whatever the tiers. A segment's entry in the manifest now also counts its tombstones. The field is optional, and a manifest without it reads as segments without tombstones, which only delays a merge of the whole database, so the manifest version stays 2.

Why the costs are logarithmic:
- A merge of F segments of tier i of at least 1 makes a segment of tier i+1 or higher, unless overwrites and deletes made it smaller, which the discarded bytes pay for. So a byte is rewritten about once per tier, and a database of n bytes has O(log n) tiers. In tier 0, each merge grows the merged segment by at least F-1 commits, so it is rewritten a bounded number of times before it leaves the tier. A merge of the whole database for the size of the newer segments reads and writes the oldest segment and the newer ones, which are at least as large and all committed since the last such merge, so it costs at most four bytes per committed byte. One for their tombstones costs at most four times the size of an entry of the oldest segment per committed tombstone, whatever the size of the database. A property test checks this bound for random streams of commits.
- Once nothing is due, every tier holds fewer than F segments, up to the tier of the largest segment, whatever the merges discarded. A property test checks this for random sizes and outputs.
- Measured with the engine on the fake store, for the same 1,000 commits with maintenance after each: 11.7 bytes read and written per committed byte at 2,000 keys and 9.4 at 20,000. Growing an empty database from 300 commits of ten new keys each to 3,000 takes it from 7.0 to 10.9, and leaves at most 16 segments.
- A cold point lookup descends into every segment whose key range holds its key, so it makes at most one GET per tree level of each live segment. With O(log n) segments and O(log n) levels, the worst case is O(log² n), but a segment below 16 KiB has one level and one of a GB has three. After many commits, the cold lookups of the request budget tests make 7 GETs where a compacted database makes 4, a lookup through a unique index 27 where it makes 9, and the join 18 where it makes 14, at 100,000 rows.

Why reads stay correct:
- Shadowing: a window holds adjacent segments, and its merged segment takes the place of the oldest of them. Every segment that was older than the window is still older than the merged segment, and every newer one is still newer. The merged segment holds the newest entry for each key among the merged ones, which is what a reader saw through them.
- Tombstones: a merge drops tombstones only when its window begins at the oldest segment, because no older segment then remains whose value a tombstone must keep hiding. Any other merge keeps them. A rebase only adds newer segments, so the oldest segment stays the oldest.
- Rebase: as before, a compaction reapplies its swap only on a manifest that extends the one it read, with all of those segments in place. The merged segments then go where their windows were, and the newer segments after all of them. When another compaction replaced segments meanwhile, whether its windows overlap or not, the compaction fails with `ErrConflict`. A compaction gives up past half the grace period, as before.
- GC: compaction's garbage is still the merged segments, and a merged segment that GC stamps as an orphan before the rebase lands is kept while it is live, as the rules of 2026-11-04 and 2026-11-07 say. Nothing in GC changes.

The simulator runs with tiers far smaller than the defaults: a fan-in of 3, tier 0 below 64 bytes, and a merge of the whole database only when the newer segments are twice the oldest. Its maintainers merge the due windows half the time, and the whole database the other half. The list-append workload through the engine keeps each list in two keys, the packed list and the values appended since, and packing a list deletes the second key, so merges meet tombstones. The fixed corpus must reach a partial compaction that rebases, a merge that keeps a tombstone, a merge of tier 2 or higher, and a compaction of several windows. The mutants `MUT-COMPACT-NON-ADJACENT`, `MUT-COMPACT-DROP-TOMBSTONES`, `MUT-COMPACT-REBASE-LOSES-SEGMENT`, and `MUT-COMPACT-REBASE-ON-COMPACTION` break the new steps, and the kill matrix and engine tests detect each. The test of `AC-6.5` also runs with `engine.Mutations.CompactAll`, which merges every segment as compaction did before, and detects it.

Alternatives considered:
- Leveled compaction, in which each level is partitioned by key range and a lookup reads one segment per level. Reads would be cheaper, but a byte is rewritten about F times per level, the manifest lists many more segments, and segments would shadow each other by level instead of by age, which the rebase and the GC rules depend on.
- Merging every segment at a threshold that grows with the database size. The cost per commit still grows with the size, only more slowly.
- Windows of exactly F segments of one tier, without the tier of newer segments. A segment that deletes made smaller than a newer one would never merge again, and such segments can pile up without bound.
- Tier 0 below one block of 16 KiB. Merges in tier 0 rewrite their merged segment until it leaves the tier, which cost 82 bytes per committed byte for commits of three keys, against 12 below 1 KiB.
- Rebasing on a manifest in which another compaction merged other segments. It looks safe when the merged segments go where their oldest live members are, but it needs its own proof, and the lease already makes such races rare.

## 2026-11-07: A disk cache bounded in bytes that evicts the least recently used entries, checks every file it reads, and belongs to one process

Context: the disk cache of `Options.DiskCacheDir` never evicted. Compaction keeps writing new segments, and every block that a read fetches went to the disk, so a long-running process filled its disk. `INV-DISK-CACHE-BOUND` now asks that the files of the disk cache never exceed a bound by more than one entry. `INV-CACHE-LOSS` still asks that any entry may vanish at any time, also in the middle of a read, and that the cache never serves wrong data.

Decision:
- **Bound.** `Options.DiskCacheBytes` bounds the disk cache of each database, and defaults to 1 GiB; zero turns the disk cache off. 1 GiB is 16 times the memory cache, holds the whole of most databases of the target workload, which are MBs to a few GBs, and the hot set of the larger ones, and a host's disk takes it easily. A file counts as its size rounded up to a block of 4 KiB, which is what most file systems allocate for it, because root blocks and the manifest are a few hundred bytes and would otherwise take up many times what the bound says.
- **Policy.** The cache is an exact LRU, a list and a map under one mutex, as the memory cache is. A read moves its entry to the front, and a write evicts from the back until the cache is within the bound. A read of a file costs microseconds and a miss a store request of milliseconds, so the mutex costs nothing that matters, and an exact LRU gives the guarantee that the tests check: an entry used within the last bound's worth of entries is a hit.
- **Writes.** A write goes to a temporary file, which is renamed into place, and the writes of one cache take turns, so that at most one file beyond the bound exists while a write runs; this is the one entry that the invariant allows. The rename and the count happen under the mutex, so a read never sees a file that the count does not know; the files of evicted entries are removed after the mutex is released, so that reads do not wait for the removals, and since writes take turns, no write can put one of those names again before its removal. A write that fails, or whose file alone would exceed the bound, drops the older value of the key, so a read never returns a value that a newer write replaced. A file that eviction fails to remove stays counted until a later eviction removes it.
- **Checked files.** A file holds a header with a magic number, a CRC-32C, and the lengths of its key and value, and then its key and value. Every read checks all of it, and a file that is missing, of another length, of another key, or damaged is a miss and leaves the cache. Writes are not synced, because a sync per block would cost more than the store read it saves, and after a power loss a renamed file can hold zeros or garbage; the check makes such a file a miss. It also refuses the files of the disk cache before this decision, which have no header, so an existing cache migrates by itself.
- **Reads that an eviction overlaps.** A read runs without the mutex. On a POSIX file system it reads the whole file even when an eviction removes it meanwhile, which is a correct value. On a file system that does not keep a removed file readable, the read ends early, and the length and the checksum refuse it. A read that fails drops only the entry it read, and not a newer one that a write of the same key added meanwhile, which must stay counted.
- **Restarts.** At open, the cache lists its directory and stats the files, and reads none of them. It counts every file in the order of its modification time, so the least recently written go first, removes leftover temporary files, and evicts down to the bound when the bound got lower. Which entries were read before the restart is not remembered. The files are at most the bound over 4 KiB, 262,144 at the default, so opening costs at most that many stats.
- **Garbage that GC deleted is not evicted early.** Only the process that runs GC learns which objects it deleted, and dropping their blocks would need an index of the cache by object. Nothing reads the blocks of a deleted object again, so they drift to the back of the LRU and go first.
- **One process per directory.** Each DSN gets a subdirectory of `DiskCacheDir`, and the process that opens one holds an exclusive lock on a file in it: `flock` on Unix, `LockFileEx` on Windows, and no lock elsewhere. Another process that opens the same subdirectory fails with `ErrDiskCacheInUse`, whose message names the directory and says to give each process a directory of its own. The lock goes away with the process, also when it crashes. Within one process, the databases of one DSN share one cache, found by the resolved path of the directory, and the last close releases the lock.

Why one process per directory: with several processes on one directory, each would count only the files it wrote, so the directory could hold the bound once per process, and each would evict files that another counts. Sharing the count needs a shared index with locking of its own, or a scan of the directory to find the files of others, whose cost grows with the directory. The checked files would keep reads correct even then, so the lock is about the bound, not about correctness, and a clear error at open is simpler than either.

The simulator runs every client's disk tier as a real disk cache over `fsfake`, a deterministic file system in memory. With `sim.Config.DiskFaults`, a client's cache is bounded to between 2 and 16 blocks of 4 KiB, so that it evicts, and a crash damages a third of its files: a flipped bit, the content of another entry's file, a lost end, or a removal, plus a temporary file left behind; between transactions, a file is damaged like that now and then. A new checker, the disk cache bound, fails a run when a client's files take more than the bound, or more than the cache counts, after any operation; no write runs between the operations of a client, so not even the one entry that the invariant allows may be there. Without `DiskFaults`, the caches are far larger than a run fills and no file is damaged, so the earlier configurations keep their histories and the kill matrix its results. The fixed corpus has 24 configurations with `DiskFaults` in every workload, and must reach `STATE-DISK-CACHE-EVICTION` and `STATE-DISK-CACHE-REFUSED`. Three mutants break the cache: `MUT-DISK-CACHE-UNVERIFIED` serves files without the check, which the checkers of the engine cells detect from seed 2 or 3, and `TestDisk` too; through SQL, a damaged table definition can make the SQL layer panic, which ends a run instead of a checker, so those cells do not apply. `MUT-DISK-CACHE-UNCOUNTED` leaves the files of an earlier process uncounted, which the disk cache bound checker detects in every cell from seed 1 or 2. `MUT-DISK-CACHE-SERVE-CUT-READ` serves a read that an eviction cut short; in the simulator no read overlaps an eviction, since a disk read does not yield to the scheduler, so only `TestDisk` detects it, through reads that an eviction or a write of the same key overlaps on a file system that cuts them short.

Measured with the read-through workload of `TestDisk`, which reads root blocks and a skewed hot set of leaves of a database, commits, and merges: 20,000 operations write 57 MB through a cache of 1 MiB, whose files never take more than 1 MiB, and 72% of the hot reads hit.

Alternatives considered:
- CLOCK, or a scan-resistant policy such as ARC. CLOCK saves the move to the front, which costs nothing next to a file read, and compaction does not write merged segments to the disk cache, so there are no scans to resist.
- Several processes on one directory, with a shared count. See above.
- Persisting the order of the LRU at close, so that a restart remembers the reads. A crash skips the close, and the order of the writes is a good start that costs nothing.
- Exact file sizes. A cache of root blocks would then take up many times its bound on disk.
- A sync of every file before its rename, instead of the checksum. It costs a disk flush per block read from the store, and the checksum is needed anyway against damage after the write.
- Dropping the blocks of the objects that GC deleted. See above.

## 2026-11-07: Checksums on every block, the manifest, and garbage batches, checked before anything is served or cached, and a catalog that is validated when it is decoded

Context: segments had no checksum of their own. The disk cache's CRC was the only check between damaged bytes and the engine; the memory cache and the store had none, and the manifest and garbage batches were plain JSON. The builder of the disk cache found that a damaged table definition, an index without columns, made the SQL layer panic in `(*table).couldScan`, and that the panic hung the simulator: a deferred `tx.Rollback` blocked forever on a lock that database/sql never released, because the panic unwound through it. `INV-DAMAGE-DETECTED` now asks that damaged bytes in any stored object, whether a block of a segment, the manifest, a garbage batch, or a definition in the catalog, give a clear error that wraps the new exported `maragudb.ErrCorrupt`, that damaged cached bytes are never served, and that damage never gives a panic, a hang, or wrong data.

Decision:
- **Blocks.** Every block of a segment ends with a 4-byte big-endian CRC-32C of the segment's object key, of the block's offset in the object as 8 big-endian bytes, and of the block's bytes before the checksum. A range GET of one block checks it without reading anything else, so no request is added; the root's location is still in the manifest, and the `AC-5.x` budgets are unchanged. The key and the offset in the checksum make a block read from another object, or from the wrong offset of the right one, fail too, where the bytes of another segment with the same layout would otherwise pass. Decoding also checks structure: every block has at least one entry, the keys in a block strictly increase, and the children of an index block lie after the child before them and before the index block itself, so no index can loop or point at itself. A scan checks that each data block it reads lies after the one before and that keys strictly increase across blocks, which bounds a walk of any index to one read per data block. The segment format has no version of its own: the manifest's version says it, and a manifest of version 3 references only segments with checksummed blocks. The overhead is 4 bytes per block, 0.02% of a 16 KiB block.
- **Manifest and garbage batches.** Both are sealed: a 4-byte magic number, `mdbm` for the manifest and `mdbg` for a garbage batch, then the CRC-32C of the object's key and the JSON as 4 big-endian bytes, then the JSON. The manifest is now version 3 and a garbage batch version 2. A manifest of version 1 or 2, which were plain JSON, fails to open with `ErrUnsupportedManifest`, whose message names both versions, as at the previous bump; the project is pre-release, so there is no migration. After decoding, the manifest is validated: every segment's root block lies within its object, sizes and counts are not negative, tombstones do not exceed the count, the smallest key is not after the largest, chain references have keys and non-negative counts, and commit records are in order and end at most at the manifest's sequence number. A garbage batch may not name itself as the batch before it. The disk cache's record of the last seen manifest is under a key that names the manifest version, `<prefix>manifest@v3`, so a record of an earlier version is never read. The keys in the checksums include the database's prefix, as the segment keys in the manifest already did, so a database still cannot move to another prefix by copying its objects. The maintenance lease is not sealed, because correctness never depends on it: a damaged lease can only make two maintainers duplicate work.
- **Where the checks run.** A block is checked before it is served or cached, whether it comes from the memory cache, which holds bytes not decoded yet, the disk cache, or the store. Cached bytes that fail are a miss: the read goes to the store, a warning is logged, and the engine counts them in `Stats.MemoryCacheRefused` and `Stats.DiskCacheRefused`. A cache returns what it was given, and only checked bytes are given to it, so this never happens without a bug, and an Antithesis `Unreachable` assertion marks it. Bytes from the store that fail give an error that wraps `ErrCorrupt` and names the object and the block; they are never cached, are logged, and are marked by an Antithesis `Sometimes` assertion and the new state `STATE-DAMAGED-READ-REFUSED`. The same holds for the manifest, in freshness reads, in the read-back after a lost acknowledgement, which simply tries again, and in Open, and for garbage batches, where a GC pass fails and deletes nothing. There is no retry of a damaged read: TLS and S3 already check transfers, so damage that the store returns is most likely lasting, such as wrong range arithmetic or a broken object, and the caller can retry its transaction.
- **Catalog.** A table definition is validated when it is decoded: its name matches its key; it has a primary key of columns in range without repeats; column names are unique and of a column type; every index has a name without NUL that no other index of the table has and at least one column, all in range, though an index may repeat a column, as in Postgres; every foreign key has columns in range, as many referenced columns, a parent and an index, sets only columns of its key, and has known actions; and the entry of an index's name holds nothing but its table's name. A foreign key is checked against the table it references when it is followed: the referenced columns are in range and of the same types, and they are exactly the columns of the parent's primary key or unique index that it names. A row that does not decode, a DEFAULT or CHECK expression that does not parse, and any definition that does not hold up give errors that wrap `ErrCorrupt`. Value decoding now rejects text that is not valid UTF-8 and times finer than a microsecond, which no write stores. `(*table).couldScan` treats an index without columns as one that Postgres could scan whole, the conservative answer, though validation makes it unreachable. Every decoder, for blocks, segment walks, the manifest, garbage batches, disk cache files, row values, and table definitions, has a Go native fuzz test whose seed corpus runs in `make test`.
- **Panics.** The simulator's scheduler recovers a panic in a task, and `Run` panics at once with a `*sched.TaskPanic` that has the task's name, the value, and the stack; the other tasks stay parked for good, because ending them would unwind code that may hold locks. A panic inside database/sql cannot be handled that way, because database/sql holds locks across the driver call and a deferred `Rollback` waits on them. So `sqldriver.Options.OnPanic`, when set, recovers a panic inside every driver call, in prepare, begin, exec, query, commit, rollback, close, ping, and reset, returns the error that OnPanic gives, and breaks the connection, which database/sql then discards. The simulator sets it, records the first panic with its stack, and panics with it again in the task once the call returned, so the run fails with the panic's value and stack under a new `panic` anomaly. The public driver leaves OnPanic unset, so an application still sees a panic as a panic; whether the public driver should recover panics too is an open question for later.

Why a checksum on the manifest rather than JSON decoding plus validation: a flipped bit in a digit or in a key yields valid JSON that no validation can tell from the real thing, such as another root offset, another segment size, or a smallest key of "b" instead of "a" that hides every key "a" of the segment. An experiment with a mutant that skipped the manifest's checksum under the simulator's damaged reads showed the worst case: a client took a damaged manifest as current, and since its ETag was the real one, its next commit's conditional write succeeded and wrote the damage back into the store, so later fresh processes failed their final reads. The seal costs 8 bytes and a CRC over a few KB per commit.

The simulator's fake store got `Faults.DamageRate`, which damages the body of a GET with a flipped bit, a cut, or the bytes of another object at the same range, while the object in the store stays whole, and counts the damage by process. `sim.Config.StoreDamage` damages one in fifty reads of the clients and the maintainers. 38 of the 298 corpus configurations run with it, in every workload, through the engine and through SQL; the soak turns it on half the time, and `make replay STORE_DAMAGE=1` replays it. The fixed corpus must reach `STATE-DAMAGED-READ-REFUSED`. Two new checkers: the cache integrity checker fails a run when a client's caches returned a block or a manifest that failed the engine's check, after any of its operations; the damaged reads checker fails a run when an operation fails with `ErrCorrupt` although the store damaged none of its reads, which means damaged bytes got past a check earlier, and when an operation through the engine fails with an error of a kind that neither the engine nor the store gives. Every segment block grew by 4 bytes, which moved segments between compaction tiers, so the histories of the existing configurations changed; the kill matrix results of the earlier mutants stayed the same apart from a few first seeds.

The new mutant `MUT-SEGMENT-UNCHECKED`, `engine.Mutations.SegmentUnchecked`, decodes blocks without checking their checksums and caches what the store returns before decoding it. It runs with damaged reads and is detected in all 12 cells, by the cache integrity checker and in some cells by the bank, list-append, unique, index consistency, and workload invariants checkers; `TestMutations` of the engine shows it serving a wrong value. `MUT-DISK-CACHE-UNVERIFIED`, the disk cache serving files without its own check, was detected only in the 4 engine cells before, by the history checkers, because the engine decoded the damaged blocks, and its SQL cells did not apply because of the panic. Now the engine refuses those blocks itself, so the history checkers no longer see wrong data, and the cache integrity checker detects that the disk cache returned them, in all 12 cells from seed 1 or 2.

Alternatives considered:
- One checksum of the whole segment, in the manifest. A range read of one block could not check it without reading the whole object.
- Checksums of the blocks in a footer or in the root. A read would need the footer first, one more GET, or the root would grow with the segment.
- A checksum of the block's bytes alone, without the key and the offset. The bytes of another segment with the same layout, or of the right segment at the wrong offset, would pass.
- xxHash or SHA-256. CRC-32C is in hardware on amd64 and arm64, the disk cache already uses it, and it detects every burst of up to 32 bits; a deliberate forgery is not the threat.
- JSON decoding plus validation without a checksum for the manifest and garbage batches. See above.
- Retrying a read whose bytes fail. See above.
- Recovering panics in the public driver as well. It would change what applications see, so it is left open.

## 2026-11-07: The driver recovers a panic in every call as `ErrInternal`, discards the connection, and never lets database/sql run the call again

Context: `sqldriver` recovered a panic only when the internal `sqldriver.Options.OnPanic` was set, which only the simulator set. In the public driver, a panic, which is always a bug in maragudb, unwound through database/sql. database/sql holds locks across a driver call, so a later call that needs them, typically a deferred `tx.Rollback`, hangs forever; this hung the simulator before the checksum decision of 2026-11-07 recovered panics there. An application that recovers the panic of a handler would leak the connection and hang the same way. `INV-PANIC-RECOVERED` now asks that a panic inside a call into the driver never reaches database/sql: the call fails with an error that wraps `ErrInternal` and holds the panic's value, the stack goes to the logger, the connection is discarded, no statement runs again because of it, and a transaction in which a call panicked never commits.

Decision:
- **Every call recovers.** Every call into the driver that does work and returns an error defers a recovery: `Connector.Connect`, which opens the engine, and `Connector.Close`; on a connection Prepare, BeginTx, Exec, Query, Ping, ResetSession, and Close; Exec and Query of a statement; Commit and Rollback of a transaction; and `Rows.Next` and `Rows.Close`. The calls without an error, such as the column types of rows, only read fields. The call returns an error that wraps the new exported `maragudb.ErrInternal`, with the message "sqldriver: internal error, a call into the driver panicked: panic: <the panic value>". The panic is a bug in maragudb, or in a custom `Options.Store` that the engine calls during the call. The panic value is formatted into the message and never wrapped, because a value that wraps `driver.ErrBadConn` would make database/sql run the statement again.
- **The stack is logged.** `Options.Logger` gets a record at the error level with the panic value and the stack. The stack is taken in the deferred call, before the stack unwinds, so it shows the frames where the panic happened. An Antithesis `Unreachable("a call into the driver panics")` marks it.
- **The connection is broken.** `driver.Validator.IsValid` then reports false, so database/sql discards the connection when the call releases it, and `ResetSession` returns `driver.ErrBadConn` as a second guard. Only a transaction or a `sql.Conn` that still holds the connection can call it again: Prepare, Exec, and Query fail with `ErrInternal`, "an earlier call on the connection panicked"; `BeginTx` and `Ping` return `driver.ErrBadConn`, because nothing has happened yet and database/sql may safely try another connection; `Commit` rolls the transaction back and returns `ErrInternal`; `Rollback` rolls back and returns nil.
- **No call that may have changed data returns `driver.ErrBadConn`.** database/sql retries a call that returns it, twice on pooled connections and once on a new one. The test mutation `exec.Mutations.PanicAfterCommit` panics right after a commit succeeded. An autocommit `UPDATE t SET v = v + 1`, plain and prepared, then fails with `ErrInternal`, and the value shows that it landed exactly once. With the recovery changed to wrap `driver.ErrBadConn`, the same test sees v = 3: database/sql ran the update three times. A transaction whose commit panics after it succeeded is committed once.
- **Outcomes.** A statement outside a transaction, or a commit, that fails with `ErrInternal` may or may not have taken effect, as with `ErrCommitUnknown`, but it is never run again. A transaction in which any call panicked never commits: its later statements fail with `ErrInternal`, and its commit rolls it back.
- **Shared state.** The engine and the disk cache are shared by every connection of a database. Deferred calls now release all of their mutexes; the few critical sections that unlocked by hand became small functions. So a recovered panic cannot leave a lock of the shared engine held. The broken connection's session is discarded with it, and other connections keep working.
- **The simulator uses the same path.** `sqldriver.Options.OnPanic` is now only an observer, `func(value any, stack []byte)`, called after the panic is logged. The simulator records the first panic and panics with it again in its task once the driver call returned, so a run still fails at once with the value and the stack.

A connection that `Driver.Open` opened closes its connector in a deferred call, so that it closes even when the rollback of its broken session panics again.

Limits: a panic in a caller's `driver.Valuer`, which `CheckNamedValue` calls, is the caller's own and is not recovered. The background maintenance loop is not a driver call; a panic there still ends the process.

Alternatives considered:
- Leaving panics alone. The hang above.
- Returning `driver.ErrBadConn` from the panicking call. database/sql would run writes again, as the test showed.
- Recovering the panic but keeping the connection. Its session is in an unknown state.
- Recovery as an option. A hang is never what an application wants.

## 2026-11-07: A parameter value that Postgres refuses when it reads it fails the same way, after analysis and before folding

Context: a `time.Time` parameter outside the range of timestamptz was stored, where Postgres refuses it. A Go string parameter that is not valid UTF-8, or that holds a NUL byte, was stored as text, whose row then failed to decode with `ErrCorrupt`, because row decoding rejects text that is not UTF-8; or it was read as bytea or as the text of a bigint, where Postgres refuses it. Both break `INV-PG-SUBSET`.

What Postgres does, measured on Postgres 18 through pgx v5.12, as the differential harness uses it:
- pgx sends a `time.Time` for a timestamptz parameter in binary, as microseconds since 2000, which it computes as `Unix()*1000000 + Nanosecond()/1000` minus the offset of 2000, so it floors the time to the microsecond. Postgres refuses a value outside 4714-11-24 00:00:00 BC to 294277-01-01 00:00:00 UTC, exclusive, with SQLSTATE 22008, datetime_field_overflow, "timestamp out of range". At the ends: 294276-12-31 23:59:59.999999999 floors to .999999 and is accepted; 294277-01-01 00:00:00 is refused; 4714-11-24 BC 00:00:00 is accepted, and so is one nanosecond later, which floors to it; one nanosecond earlier floors to 23:59:59.999999 the day before and is refused. The years from 4714 BC to 1 BC are accepted and written with a BC suffix.
- Postgres reads the parameters' values at Bind, after it analyzed the statement and before it folds constants. `SELECT $1::timestamptz, nope` fails with 42703, undefined column; `SELECT $1::timestamptz, 1 / 0` fails with 22008, also in a branch that never runs, such as under `WHERE false`; and in a transaction the failure aborts it, so the next statement gives 25P02.
- pgx overflows: for a time more than about 292,277 years from 2000, the microseconds overflow 64 bits and wrap around, and Postgres may then accept another time. The year 600000 arrived as 15445-12-13 and the year -300000 as 284554-01-18, and exactly the largest and the smallest 64-bit values mean infinity and -infinity there. maragudb refuses every such time as out of range, which is what Postgres does with the time itself; the harness draws times only within the range that pgx encodes faithfully.
- pgx sends a Go string as text for a parameter of any type. Postgres checks the encoding of the text when it reads it, and refuses text that is not valid UTF-8, or that holds a NUL byte, with SQLSTATE 22021, character_not_in_repertoire, `invalid byte sequence for encoding "UTF8": 0xff`, whatever the parameter's type: text, bigint, double precision, bytea, or timestamptz.
- Checked with no gap found: float64 NaN and plus or minus infinity as double precision are accepted on both sides with equal results; a float64 where a bigint or a timestamptz is inferred is `ErrUnsupported` in maragudb, and pgx even sends NaN as the bigint 0; an int64 that does not fit an integer parameter is refused by pgx before it sends anything, and fails with `ErrOutOfRange` in maragudb; a `[]byte` for bytea holds any bytes on both sides; a `[]byte` in a text context, which pgx sends as text that Postgres checks for UTF-8, is `ErrUnsupported` in maragudb (`UNS-PARAMETERS`).

Decision:
- **Times.** A `time.Time` parameter is floored to the microsecond and must lie in the range of timestamptz, from 4714-11-24 BC to the end of 294276 UTC, or the statement fails with `ErrOutOfRange`, "timestamp out of range". Parameters before the year 1 are accepted, because Postgres accepts them, and maragudb already compared, stored, and wrote them with BC as Postgres does; text input still reads only from the year 1 on (`UNS-TIMESTAMP-INPUT`). The type table in requirements.md now gives the Postgres range.
- **Strings.** A string parameter that is not valid UTF-8 or that holds a NUL byte fails with the new exported `maragudb.ErrInvalidUTF8`, SQLSTATE 22021, whatever type it has.
- **Order.** The binder checks a parameter's value when it meets the parameter, records the first refusal on the session, and lets the parameter stand in for a value that analyzes the same: NULL for a string, which every type reads, and a time in range for a time. A time is a timestamptz in every statement that maragudb accepts; in any other context it is already `ErrUnsupported`. Every statement reports the recorded error where it reports folding errors, before the first of them; a subquery that is only being analyzed does not report it, its statement does; and the session reports it as a last resort when the statement would otherwise succeed. Errors that maragudb finds during analysis come first, as in Postgres, and the failure aborts an explicit transaction, as in Postgres.
- **Stored times.** Row decoding also refuses a stored time outside the range, as damaged data (`ErrCorrupt`), since no write stores one any more. The project is pre-release, so a database that an earlier version filled with such a time fails to read it.

Harness: the differential generator now puts parameters into the values of INSERT, in non-key columns, one in six, and into the SET of UPDATE, one in eight. Their values are Go values of the column's type, the value's text as a string, nil, times near both ends of the range and the year 1 with offsets of nanoseconds to a day, times before the year 1, and strings that are not UTF-8. A parameter that pgx refuses to encode counts as a failure on both sides, and the harness aborts the Postgres transaction to match. The error classes of the harness map 22008 to `ErrOutOfRange` as well, which also covers `'294277-01-01'::timestamptz`, which maragudb already failed with `ErrOutOfRange`, and 22021 to `ErrInvalidUTF8`. The parameter property test draws boundary times and invalid strings in every context.

A literal in the SQL text that is not valid UTF-8 was a syntax error in maragudb's lexer, where Postgres gives 22021; the decision of 2026-11-07 on parameter types and the order of Postgres's errors fixes it.

Alternatives considered:
- Checking the values in the driver before the statement runs. Errors of analysis would come after it, and the session's transaction would not abort.
- Keeping the year 1 as the lower bound for parameters, and rejecting earlier times with `ErrUnsupported`. Postgres accepts them, and maragudb already handles them.
- Reporting invalid UTF-8 as `ErrCast`. It is not a cast.
- Copying pgx's wraparound. It is a bug of pgx, not Postgres behavior.

## 2026-11-07: A SELECT on one table whose rows may be read in another order than the key is rejected when its rows fail with different errors

Context: a `SELECT` on one table failed on the first row in key order that failed, which is the row Postgres fails on when it scans the primary key forward, and the differential harness reruns Postgres with the rows in key order when the error classes differ. The harness found a statement where that is the wrong row: `SELECT abs(o.c0), NULL FROM t AS o ORDER BY (SELECT min(s21.c0) FROM t AS s21 WHERE 10 / (s21.c0 - s21.c0) >= ...), o.c0 DESC` over the rows -9223372036854775808 and 9223372036854775807. Postgres scanned the key backward, `abs` of the highest key succeeded, and the subquery then failed with 22012; maragudb failed `abs` of the lowest key with 22003. Measured on Postgres 18 with `enable_seqscan` off, with `i` the primary key of `t`:
- `SELECT abs(j), 10 / j FROM t ORDER BY i DESC` is an `Index Scan Backward`: Postgres evaluates the output on the rows in descending key order and fails on the row with the highest key first. With `ORDER BY i` it scans forward and fails on the lowest key first.
- A constant sort key is dropped, so `ORDER BY 1 + 1, i DESC` and `ORDER BY (SELECT min(i) FROM t), i DESC`, whose uncorrelated subquery is a constant, also scan backward.
- `ORDER BY a DESC, b` on a primary key `(a, b)` scans backward with an `Incremental Sort`.
- `ORDER BY i DESC NULLS LAST` is a full sort, which evaluates the output in key order.
- Whether Postgres scans backward or sorts is a decision of cost: with `WHERE a = 1 ORDER BY a, b DESC` it chose a bitmap scan and a sort on a tiny table.
- Within one row, the output is evaluated before the sort keys, as in maragudb.

Decision: a `SELECT` on one table whose rows Postgres may read in another order than the key evaluates every row. That is one with a sort key in descending order, any key, since a constant key is dropped and a key equated with a constant drops out of the order, and one whose rows come from a subquery in `FROM` or a CTE, which Postgres merges into the query or reads in the order of its own plan. When the rows fail with different classes of error, the statement is rejected with `ErrUnsupported`, "rows of this query fail with different errors"; when every failing row fails with the same class, that error is reported, as Postgres does in every order; and a row whose error is itself `ErrUnsupported`, such as a subquery that fails, rejects the statement. Every other `SELECT` on one table keeps failing on the first row in key order, which matches Postgres scanning forward. Joins and grouped queries already had the same rule. The first 10,000-case run with this rule found the same question inside one row: `SELECT sum(DISTINCT c0)::double precision FROM t WHERE CAST(c1 AS bigint) > 1 GROUP BY c2, c0 HAVING 10 / c2 > 0`, whose `HAVING` condition Postgres moves into `WHERE`, failed with 22012 on Postgres and 22P02 on maragudb on a row where both conditions fail, because Postgres evaluates the conditions of `WHERE` in the order of their estimated cost, and the division is cheaper than the conversion through text, whatever the written order, as EXPLAIN shows in its `Filter`. So a row on which two conditions of `WHERE` fail with different classes of error also rejects the statement, whatever the other rows do. `TestRowOrder` in `/internal/pgdiff/plans_test.go` pins the plans and the outcomes.

Alternatives considered:
- Emulating the backward scan, and failing on the highest key. Whether Postgres scans backward or sorts is a decision of cost, as the bitmap scan above shows.
- Rejecting every `SELECT` on one table whose rows fail with different errors, as for joins. Key order is the plan Postgres uses with its primary key in every other case, and the harness reruns Postgres in key order to check it.
- Limiting the rule to a descending key on a column of the primary key. A constant key, or a key that a condition equates with a constant, drops out of Postgres's order, so the key after it decides the scan.

## 2026-11-07: A subquery is uncorrelated when folding drops its references to the queries around

Context: the subquery decision of 2026-11-07 evaluates an uncorrelated scalar subquery in `WHERE`, `ON`, or `HAVING` before any row, and a correlated one on each row that reaches it, and maragudb told the two apart by the references the subquery writes. Postgres decides whether a subquery is correlated after it folds constants. The differential harness found `DELETE FROM t AS o WHERE (SELECT CASE WHEN (SELECT FALSE FROM t AS s12 WHERE s12.c0 = o.c0 AND CAST('off' AS boolean) ...) THEN ... Alternatives considered:
- Deciding correlation on the AST with a folder of its own. A second folder could disagree with the binder's.

## 2026-11-07: Parameters are typed in the order in which Postgres analyzes the statement, and a statement is analyzed again when a later reference has the parameter's type

Context: the decision of 2026-11-07 "Parameters get one type from their contexts, and Postgres's errors for undetermined types and refused values come in its order" read every reference of a parameter like a quoted literal of its own, recorded the type that each context gave it, and rejected with `ErrUnsupported` a parameter whose contexts gave it different types, or a type in one context and none in another, such as `IS NULL` or `count()`. That refused `WHERE k = $1 OR $1 IS NULL`, the common way to write an optional filter, which Postgres accepts. This decision supersedes the "One type" bullet of that decision and its first two alternatives; the rest of it stands.

What Postgres does, measured on Postgres 18 through pgx:
- A parameter gets its type at the first reference that a context coerces to a type, in the order in which Postgres analyzes the statement. Every reference it makes after that has that type, as a typed value. A reference made before then is coerced later; when that coercion is to another type, or the reference sits in a context that gives no type, `IS NULL` or `count()` without `DISTINCT`, Postgres fails with 42P08, "inconsistent types deduced for parameter" or "could not determine data type of parameter". So `k = $1 OR $1 IS NULL` works, `$1 IS NULL OR k = $1` fails with 42P08, `($1::bigint IS NULL OR k = $1)` works, and `coalesce($1, k)` and `k = coalesce($1, k)` work.
- A later reference keeps the type, and its context converts it implicitly or fails: `SELECT $1 + 1, $1 + 5000000000` types `$1` integer, and the second reference adds an integer to a bigint; `WHERE k = $1 AND s = $1` on a bigint `k` and a text `s` fails with 42883, operator does not exist: text = bigint; `WHERE f = $1 AND k = $1` on a double precision `f` and a bigint `k` works; `SELECT $1::bigint, $1 || 'x'` gives `1x`.
- The order of the analysis: the `WITH` clause, each CTE in order; `FROM`, with the condition of each join after both of its sides; the output list; `WHERE`; `HAVING`; `ORDER BY`; `GROUP BY`; `DISTINCT`; `OFFSET`; `LIMIT`. An output column that is a bare parameter gets the type text at the end of its query, or earlier where `ORDER BY`, `GROUP BY` by position or name, or `DISTINCT` reads it, so `SELECT $1, $1::bigint` fails with 42P08 and `SELECT $1::bigint, $1` works. Within an expression, the operands come before the operator that coerces them; `AND`, `OR`, `NOT`, and the `WHEN` of `CASE` coerce each operand to boolean right after it; the operand of a simple `CASE` becomes text right after it; and the query of an `IN` subquery is analyzed before its left side. Subqueries are analyzed where they are. `x BETWEEN a AND b` is `x >= a AND x <= b` with `x` analyzed twice, so a parameter in `x` has its type from the first comparison in the second. The left side of `IN (list)` is one reference that Postgres compares with each item, so items of different types give 42P08 unless the parameter already has a type. `UPDATE` analyzes `WHERE` before `SET`, and every `SET` expression before it coerces them to their columns; `INSERT` analyzes each `VALUES` row and then coerces its items to their columns, one row after the other.
- `count(DISTINCT $1)` gives the parameter the type text, because `DISTINCT` sorts the argument; `count($1)` and `IS NULL` give none. Unary `+` of an unknown is double precision: `SELECT +'2'` is 2 and `SELECT +NULL` is NULL. Unary `-` of an unknown is ambiguous, 42725.
- Errors keep Postgres's order: an analysis error that Postgres meets before a 42P08 comes first, and the value refusals of parameters come after the whole analysis, for the lowest parameter number, as before.

Decision:
- **Order.** At Prepare, a walk of the statement in Postgres's analysis order gives each reference of a parameter the position where Postgres makes it and the position where its context coerces it, and gives each expression a position. The binder still reads each reference like a quoted literal and records the type its context gives it. Once the statement is analyzed, the ledger replays Postgres's typing over these records in that order. A reference that Postgres makes before the parameter has a type, and that a later context coerces to another type or that reads where no type is given, fails with `ErrType`, as Postgres fails with 42P08; the harness maps 42P08 to the type class, next to 42804, 42883, 42725, and 42P18.
- **Analyzed again.** When a reference that Postgres makes after its parameter has a type got another type from its context, the statement is analyzed again with that reference bound with the parameter's type, so that its context converts it implicitly or fails as Postgres does. This repeats until the types settle, at most once per reference, before the statement reads or writes anything. A statement whose analysis fails is checked against the same order: a 42P08 that Postgres meets before the failing expression comes first. For `BETWEEN`, the walk at Prepare gives the tree a copy of the left operand for the second comparison, unless the operand has a subquery, so its references are separate.
- **Unsupported.** Three cases stay `ErrUnsupported`, which `UNS-PARAMETERS` names. A Go value that would need a conversion to the one type that Postgres gives the parameter, as before; `WHERE i = $1 AND j + 0.5::float8 > $1` with a float64 is rejected, because `$1` is a bigint. A parameter that is an output column and that `ORDER BY` names by the same parameter, or `GROUP BY` by the output column's alias, when its contexts give it different types, because whether Postgres takes the item for the output column depends on the type the parameter has by then; and likewise any reference that maragudb analyzes in contexts of several types where Postgres has one, such as the left side of `BETWEEN` when its operand has a subquery, or the left side of an `IN` in a subquery whose list reads columns of the query around, which Postgres compares as an array of constants. A statement whose analysis fails, in Postgres too, before maragudb has analyzed every reference of a repeated parameter that Postgres analyzes before the failing point, or where the failure has no position in Postgres's order, such as a `VALUES` item of the wrong type for its column, because the types of those references could make Postgres fail with another error first.
- **Fixes found on the way.** `count(DISTINCT $1)` gives the parameter the type text, and unary `+` of an unknown is double precision, as in Postgres. For `IN` with a subquery in `WHERE` or in the condition of a join, Postgres can make a semi-join whose hash join computes the left side as its key on every row of the query around, also when the subquery has no rows for that row, where a subplan never computes it; EXPLAIN on Postgres 18 shows `Hash Join` with `Hash Cond: ((SubPlan 3) = s20.c0)`. maragudb evaluates such a left side, when it can fail, also on the rows for which the subquery has no rows, and rejects the statement when it fails there, under `UNS-PLAN-DEPENDENT-SUBQUERY`: `SELECT * FROM dev WHERE 10 / j IN (SELECT i FROM dev2)` with a row where `j` is 0 and an empty `dev2`. The differential harness found it. It also found that Postgres folds a `WHERE` that a NULL conjunct decides to false, as EXPLAIN shows with `One-Time Filter: false`, so that `s11.f3 = o.f3 AND NOT NULL` drops the reference to the query around, where the decision of 2026-11-07 on correlation after folding kept it; such references are now dead too, which can only make maragudb reject more. And a simple `CASE` evaluated each `WHEN` value before its operand, so `CASE abs(c0) WHEN c0 / 0 THEN 1 END` failed with division by zero on a row where Postgres, which evaluates the operand first, fails with 22003; the operand now comes first.

- Implementing Postgres's inference inside the binder in one pass. The binder's clause order differs from Postgres's, and it binds some expressions several times for planning.

After 300 small updates the manifest is 6,878 bytes against 6,241 without filters, with six filters of 395 bytes in it. A compacted database of that size has no filter at all.

Alternatives considered:
- Several key ranges per segment in the manifest. They would prune scans too, but random updates spread a segment's keys over the whole key space, where a range excludes little; a Bloom filter excludes about 99% of absent keys. They could come later for scans.
- Every filter in the manifest. The filter of a segment of 100,000 keys is 125 KB, and every cold start reads the manifest and every commit writes it.
- A filter object per segment, or one for all segments. One more GET per segment or per manifest, and more objects for GC.
- Filters for the largest segments, or filters split by key range. The first read of a large segment would fetch megabytes, and a split filter needs the root first, which saves nothing in a tree of two levels.
- Filters of key prefixes, for scans of the entries of a non-unique index. The engine would need the SQL layer's key layout, and compaction rebuilds filters from keys alone. Measured, such lookups already cost here what they cost compacted.
- Skipping the filter when a cache holds the root block but not the filter block. In a tree of two levels, the filter costs the GET it may save, but in a deeper tree every lookup of an absent key would descend, and the filter would never come back into the cache while the root stays there.
- Going on without the filter when its block is damaged, since the filter only saves requests. Damaged bytes from the store fail with `ErrCorrupt` everywhere else, as `INV-DAMAGE-DETECTED` asks, and a lookup that skipped the check would hide lasting damage.
